### ba70b16 — Allow app-drawn subtitles from a home-network server over plain HTTP (bug B-20.3)
- Verdict: ACCEPT
- What it does: Allows the subtitle document to be fetched over HTTP from the existing local/private address classes on Apple and Android. It retains the media-origin, grant/resource/revision, path, credential, redirect, timeout and byte-bound checks.
- Findings:
  1. **Nit — `apps/native/Native/PorticoSubtitleSelection.m:21–41`; `apps/native/android/app/src/main/java/tv/getportico/portico/native/PorticoSubtitleSelection.kt:278–299`: distinguish address classification from full URL validation in the report.** The helpers are subsets of/equivalent to `privateRouteHost`, not complete ports of `routeOrigin`. Actual Kotlin helper counterexamples against **routeOrigin** include `[fc00::0001]` and `[fc00:0:0:0:0:0:0:1]` (refused as noncanonical by core) and `[fc00:::1]` / `[fc00:]` (refused as invalid URLs). Core's **privateRouteHost also returns true** for these; this is not evidence of a newly admitted public address. Update the parity claim and, if the native boundary is later exposed to raw URLs, validate complete IPv6 syntax and catch URL-builder rejection before fetch. Do not present the malformed-host experiment as a proven network request or device crash.
  2. **Nit — lane report B-20.3 test note:** add negative controls. The current LAN/HTTPS/embedded-track checks would also pass a wrong implementation that allows all HTTP. On both platforms, exercise native apply with otherwise valid source/document pairs on the same public HTTP origin (`8.8.8.8`, a public DNS name, `2001:db8::1`); assert invalidation and no request. Also reject cross-origin documents, IPv6 zone identifiers, legacy/zero-padded IPv4, and redirects; test canonical ULA/link-local IPv6. No live public service is needed: use an instrumented request sink/native test fixture.
- Trust-boundary trace: `packages/client-core/src/route-identity.ts:42–54` permits HTTPS anywhere and HTTP only to localhost, loopback, `.local`, RFC1918 IPv4, IPv4 link-local, ULA or IPv6 link-local. Neither native helper adds CGNAT/Tailscale 100.64/10, public IPv4, public IPv6 or IPv4-mapped IPv6; that preserves D-07 rather than deciding it. The native IPv6 conditions force exactly four hex characters before the first colon and one of the same prefixes. Subsequent syntax checking is weaker than a URL parser, but stronger than the shared host predicate. The `.local` character restriction is stricter. Nil/empty/oversized values return false; IPv4 numeric accumulation is bounded and safe.
- Production reachability: `packages/client-core/src/subtitles.ts:53–61` requires a relative grant-bound document path; `apps/native/src/player/usePlayer.ts:298–304` resolves it with `new URL(..., api.baseUrl).href` before passing it to the native bridge. Connection creation/restore uses core `routeOrigin` (`server-connections.ts:27–28,69–72`). Thus the malformed/noncanonical raw helper examples are not a demonstrated bypass of this shipped JS path. I found **no host the new helper admits that privateRouteHost itself refuses**, and no public-HTTP request bypass. This conclusion is narrower than platform parser/runtime validation.
- Native code review: the change adds only synchronous local helper logic. Objective-C selectors/types are valid by inspection (`NSString` casing/substring, character sets, array indexing); nil `url.host` is safe. Kotlin nullability/index guards and integer parsing are safe. Existing main-thread application, lifecycle, scoped binding, redirect denial and request limits are unchanged on both platforms. Existing `NSURLSession` delegate runs on the main queue; OkHttp callbacks still post results to the main handler. No new user-facing string or canonical-package edit.

  - All native TypeScript/Node/i18n checks PASS (243/243).
  - In-memory Node differential probe against the actual core exports: 65,536 IPv4 first-two-octet combinations and 65,536 four-digit IPv6 first-hextet combinations matched a literal transcription of the native algorithm.
  - Re-ran the lane's **existing compiled standalone Kotlin class** and reflection harness via Java, feeding `/dev/stdin`; compared 131,082 results with actual core exports. ### fdd0652 — Make Next and Previous move through the queue for video playback (bug B-20.16)
- Verdict: REJECT
- What it does: Routes transport, mini-player and system Next/Previous to the installed device queue when native listening does not own playback, retaining audio-owner dispatch and the guide's separate channel-step branch. It corrects ordinary video-queue no-ops but misses group ownership and an unavailable-next case.
- Findings:
  1. **Blocker — `apps/native/src/player/VideoPlayer.tsx:246,277–278,454`; `apps/native/src/player/queue-step.ts:22`: new Previous handling bypasses Watch Together's control boundary.** Core `V1QueuePlayer.previous()` (`packages/client-core/src/playback-v1/v1-queue-player.ts:488–493`) calls `PlaybackService.seek(0)` directly after three seconds. That skips `engine.seekTo` / the installed `groupControl` (`usePlayer.ts:530–533`; `app/together.tsx:48–60`). If a viewer is already playing the group's current item in a multi-entry device queue, the follower need not load a new title; the queue and enabled Previous remain. A host's Previous then seeks only that device; a participant's Previous also seeks locally despite the host-only rule. The follower can undo the seek, making it appear broken. Next/early Previous similarly address the device queue rather than the group queue. This does **not** grant server authority over the group, but it introduces unsynchronized local playback commands where the contract requires group-owned intents. Sharing/social contract §11 (line 249) explicitly assigns group next/previous/seek to the host. Route queue actions through an engine handler that first consults group ownership and dispatches the existing group transport, refusing participant actions; use the device helper only outside a matching group. At minimum, guard these new local actions while group-owned playback is active. Add host/participant tests for Previous beyond three seconds and Next/Previous queue changes. "Matches web" does not justify the regression.
  2. **Should fix — `apps/native/src/player/queue-step.ts:24`, with `VideoPlayer.tsx:239` / `MiniPlayer.tsx:22`: enabled Next still silently does nothing when the immediate next entry is unavailable but a later entry is playable.** The UI enables Next by finding any following available entry; core `V1QueuePlayer.accept()` (`:253–256`) sets `view.next.available` only from the immediate following entry. With `[current, hidden, playable]`, the real adapter produces `next.available=false`, the button is enabled, and this helper sends no request. The server can skip withheld entries in a bounded walk (`apps/portico-server/server/internal/playbackv1/queue_commands.go:1027–1074`). For an explicit Next intent, forward the current queue ID/revision to the controller when a current queue exists and let the server resolve the bounded advance/refusal; reconcile button/system capability state with that behavior. Add a regression using the real adapter's unavailable entry, not just a manually toggled boolean. Preserve true end-of-queue behavior and native listening.
- Tests run: All native checks PASS, including test TypeScript (243/243). The four new tests catch the original dispatch defect: an in-memory substitution of the old `systemListeningAction` behavior made three fail and the audio-owner test pass, as reported. A separate in-memory probe called the real `V1QueuePlayer.accept` and this helper with current/hidden/playable entries: UI predicate true, `next.available=false`, zero Next calls. Calling the real `previous` through the helper with position 10 seconds produced a direct local `seek(0)`. Source tracing shows it cannot reach the group handler; no device/server reproduction is claimed. No files were changed for these probes.
- Residual risk: Device remote/system command delivery, TV channel stepping, audio-owner handover, queue replacement/retry and focus need acceptance. The lane's standard season/audio/live test note is useful, but must include unavailable entries and host/participant Watch Together cases before accepting this fix. The reported group-seek residual risk is an actual new wrong dispatch, not merely unverified hardware behavior.

### B-19.1 — Cold-launch link thrown away
- **Audit correction justified; blanket “design change” skip not justified.** The lane correctly found a replay path missed by both audit passes: restore calls `commitSelectedViewer` (`session.tsx:458–460`); its fence clears the viewer (`:396–400`), then publishes the real API/viewer (`:368–375`). Core `ViewerSelectionCommit.commit` awaits durable storage and server verification between fence and publish (`viewer-selection.ts:56–60`), while `App.tsx:22–25` removes/remounts Shell across signed-out/ready phases. A persistent launch-options URL can therefore be read again by `Shell.tsx:294` after successful restore. “Nothing ever replays” and “all cold links are lost” are too broad. This source path is not device acceptance of every launch source.
- The narrower actual defects are still within the stated deep-link objective. `Shell.tsx:259,294–296` drops URL events until a real origin exists, while iOS `PorticoIntents.swift:13–19` schedules some entry sources once after two seconds. Slow/offline restore can lose that event. Conversely, `getInitialURL` is re-read on every later Shell mount without a consume marker or expiry. NAV-11 explicitly requires a single bounded pending intent, an approximately ten-minute expiry, viewer/server binding, supersession/discard rules and exactly-once consumption (`navigation-and-input/contract.md:215–231`). These are already decided behavior, not a new product feature or an open D-number.
- **Recommended follow-up:** one process-level pending-link owner above Shell, preserving native allowlists and dispatching only after the existing viewer fence/real-origin readiness. Read the initial URL once, buffer at most one stamped event, consume once, and discard on expiry/cancel/scope mismatch. Reuse that owner for B-21.14's async completion fence. The lane describes essentially this correct repair but supplies no >one-day estimate or unresolved contract choice that warrants skipping it. It should remain an actionable scoped defect in this pass/handoff, not be presented as waiting for Justin to redesign navigation.
- Acceptance tests: URL event during a deliberately >2-second restore dispatches once after readiness; initial URL followed by renewal/remount does not replay; sign-out/profile/server switch fences old asynchronous dispatch; a newer link supersedes the old one; expired and mismatched intents do nothing. Run device entry checks for launch URL versus user-activity/universal-link delivery separately.
