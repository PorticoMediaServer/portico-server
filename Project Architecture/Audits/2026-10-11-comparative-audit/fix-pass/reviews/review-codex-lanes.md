### 6777e0b — Accept signed secure LAN route aliases  (bug B-22.1)
- Verdict: **ACCEPT**
- What it does: `verifyRoutes` used to require every `class:"lan"` candidate to have a private-literal / `.local` / `localhost` host. It now also accepts, for `lan` only and HTTPS only, a host matching exactly `l-<32 lower hex>.ptc-<19 base32><a|q>.direct.getportico.tv`. Everything else in `verifyRoutes` (signature, key id, audience, server id, pin, expiry, generation bounds, canonical-origin round trip, duplicate refusal, 24-candidate cap) is untouched.
- Defect is real: Hosted rewrites every HTTPS LAN literal to that alias before signing (`internal-hosted/hosted-services/hosted/internal/postgres/routes.go:164-172`, `dns/directdns/table.go:35`), so any server with a trusted-TLS LAN listener produced a document the client rejected outright with `invalid_routes` — all candidates lost, not just the LAN one.
- Trust-boundary trace (the part I spent most time on):
  1. **No new destination becomes reachable.** Before this commit the very same origin was already accepted with `class:"public"` or `"manual"` (any HTTPS host is). I confirmed this with a probe script: `https://l-…ptc-….direct.getportico.tv:32500` verifies as `public` on the base rule. The change only alters which *class label* the name may carry.
  2. **What the `lan` label buys.** I grepped every consumer (`packages/client-core/src/route-connection.ts:112-125`, `server-admin/status-words.ts`, web, native `src/`): the class is used only to order the probe race (LAN first, public held back 120 ms, two LAN probes at once). It never permits plaintext, never skips `probeRoute`, never widens what is sent. Credentials still go only to an origin that returned a nonce-bound proof signed by the pinned server key.
  3. **Plaintext is not widened.** `routeOrigin` (line 58) still rejects `http:` for anything `privateRouteHost` does not accept, and `privateRouteHost` is unchanged (the alias is deliberately not added to it; the new test asserts `privateRouteHost(alias) === false` and that `http://alias` throws).
  4. **Regex soundness.** Anchored `^…$` with no `m` flag, tested against `URL.hostname` (already lower-cased/punycoded), after `routeOrigin(c.baseUrl)!==c.baseUrl` has forced a canonical ASCII origin. The namespace part matches Hosted's canonical encoder exactly: 12 bytes → 20 unpadded base32 characters whose last character carries one data bit, so only `a` or `q` (`dns/directdns/codec.go:92-103`). The label part matches `ValidMemberLabel` (32 lower hex).
  5. **Adversarial inputs I ran** (all rejected as `lan`): trailing dot (with and without port), upper-case host, upper-case hex label, extra leading label, suffix appended (`….direct.getportico.tv.evil.example`), near-miss zones (`.tvx`, `xdirect.`, `direct.getportico.t`), dot-for-any-char substitutions in each literal dot position, 31/33-char labels, non-hex label, non-canonical namespace tail (`…1`, `…c`), Unicode hyphen, fullwidth dot (IDNA maps it to `.`, then the canonical-origin comparison rejects the raw string), dotless-i / cedilla homoglyphs, `xn--` prefix, userinfo (`alias@evil`, `alias:port@evil`, backslash form), path/query/fragment smuggling, `%2e`, embedded newline, explicit `:443`, hex port, empty port, bracketed host, `ws://`, `HTTPS://`, IPv4 legacy forms (`0x7f.1`, `127.1`, `2130706433`), IPv4-mapped IPv6, zoned IPv6, `foo.local.`. Accepted as expected: the alias with and without port, the `…q` namespace variant, private IPv4/IPv6 literals, `foo.local`, `http://localhost:1`.
  I could not find a hostname the new rule accepts that it should not.
- Findings:
  1. **Nit** — `packages/client-core/src/route-identity.ts:53`: the zone `direct.getportico.tv` is now hard-coded in the client as well as in Hosted (`postgres/routes.go:155,167`). A development or staging Hosted with a different zone would again produce documents this client rejects. Not a defect today (Hosted hard-codes the same literal); worth a comment or a shared constant when the zone is next touched.
  2. **Nit** — the React Native copy `portico-react-native/packages/client-core/src/route-identity.ts` is still byte-identical to the server base (I diffed it), so native clients keep rejecting these documents until the packages are mirrored (`node scripts/shared-packages.mjs --write`). The lane says this ("mirror later"); it must not be forgotten, and that repo's CI check will fail until it is done.
- Tests run:
  - `node --experimental-strip-types --test packages/client-core/test/route-identity.test.ts` → 2/2 pass. The acceptance test necessarily fails on the base rule (alias as `lan` → `invalid_routes`); the rejection test is meaningful (11 near-miss origins plus wrong audience and wrong signature).
  - My own adversarial script (47 rejects, 8 accepts, listed above) → all as expected.
  - `npm run test:core` → 1456/1456 pass.

### 7e4ffcb — Deduplicate signed route origins after name normalization  (bug B-22.2)
- Verdict: **ACCEPT**
- What it does: in `Store.RouteSets`, after the existing public-label and LAN-alias rewrites, a candidate whose final `BaseURL` already exists in that server's set replaces the earlier one only if it has a newer generation, or the same generation and `reachable` quality; otherwise it is dropped. Position of the first occurrence is kept.
- Defect is real: two HTTPS LAN literals on one port (IPv4 + IPv6, or two interfaces) collapse to one alias origin, and a current and a previous public label collapse to the current label; the client refuses duplicate origins (`route-identity.ts:90`), so the whole document was rejected.
- Traced:
  - **Signing covers exactly what clients verify.** `RouteSets` is the only producer (`directory/service.go:188` is the only caller); `signRoutes` (`directory/routes.go:132-152`) marshals `set.Candidates` as given and signs those bytes. De-duplication happens before signing, in the projection; nothing is altered after the signature.
  - **Cannot drop a distinct address.** The key is the full final origin string (scheme, host, port). Different ports, `http` literals (never rewritten) and different servers (the set is per server id) stay distinct; the new test covers each. The only things merged are rows that already had identical origins, which the client would have rejected anyway.
  - **Ordering.** The client re-sorts by last-good, class, quality (`route-connection.ts:113`), so document order carries no meaning beyond a stable tie-break; keeping the first position is fine.
  - **Mixed-class collision** (e.g. a `manual` row that literally names the current `c-`/`l-` host and a rewritten row): the survivor's class is whichever wins on generation/quality. Both classes are valid for that origin on the client after B-22.1, and the pair was a hard reject before, so this is harmless.
  - Cost: O(n²) over at most ~24 candidates per server. SQL unchanged.
- Findings:
  1. **Nit (pre-existing, not introduced here)** — `postgres/direct_route.go:299-319` publishes at most one private IPv4 and one IPv6 for the alias, and ignores link-local literals that `validRouteCandidate` accepts. A server with two private IPv4 interfaces, or only a link-local HTTPS LAN address, therefore has an alias that does not resolve to every address it reported. De-duplication does not cause this (the alias rewrite already discarded the literal), but it is now the visible behaviour rather than a rejected document. The lane noted it as out of scope; I agree.
  2. **Nit** — `routes.go:181`: on equal generation a `reachable` duplicate replaces an already-`reachable` entry. Harmless (identical apart from class), but `&& previous.Quality != "reachable"` would make the intent exact.
- Tests run:
  - `go test ./internal/directory -count=1` (GOPROXY=off) → ok.
  - `internal/postgres` **cannot be compiled on this machine** (pgx, go-oidc, miekg/dns, oauth2 are not in the module cache; I did not download). So neither new test has been run by me or by the lane in the real package; the lane ran a source-copied harness only. I read both tests against the fixtures: `routes_candidates_test.go` drives the real `RouteSets` through a fake `database/sql` connector (implements `QueryerContext`, ten columns matching the `Scan`), expects 5 candidates from 9 rows and would fail with 9 on the base code — correct. `routes_secure_lan_test.go` follows the existing `member_label_test.go` fixture pattern (`setup`, `certificate_namespaces` insert, `fixture_installed_claim`) and its expectations follow from the code; it needs PostgreSQL.
  - `gofmt -l` on the changed files → clean.
- Residual risk: the package must be compiled and `go test ./internal/postgres ./internal/directory` run where the dependencies and a disposable PostgreSQL exist (the lane's command block is specific and correct; note CI uses `postgres:17`, the note says 18 — either is fine). Until then B-22.2 is an unverified build. Deploy order: ship B-22.1 to clients before or with this, otherwise the now-well-formed document is still rejected by old clients for its `lan` alias (no worse than today).

### 890e7cf — Force hardware encoder keyframes to start independent segments  (bug B-03.1)
- Verdict: **ACCEPT**
- What it does: after the shared `-force_key_frames expr:gte(t,n_forced*N)`, `BuildConversion` appends `-forced-idr 1` for NVENC and `-forced_idr 1` for Quick Sync and AMF. Software, VA-API and VideoToolbox get nothing extra.

  - **Quick Sync** — option is spelled with an underscore (in the common QSV options, so also valid if HEVC/AV1 QSV are ever added); `qsvenc.c:2481-2484` adds `MFX_FRAMETYPE_IDR` when set. Correct.
  - **AMF** — underscore, boolean; `amfenc.c:505-512` requests an IDR and inserts SPS/PPS. Correct.
  - **VA-API** — no such option exists; adding one would make FFmpeg exit. The commit rightly adds none (`vaapi_encode` already treats a forced `I` as IDR).
  - **VideoToolbox** — no option needed or added.
  - No argument allow-list elsewhere rejects the new flags (I searched for every use of `-force_key_frames`), and the option is appended only when a video encoder is present in the same output, so there is no "option not used by any stream" case. Live TV / Library Channels (`linear_hls.go:93`) build with no hardware probe, so they are unaffected.
- Comparison with Jellyfin: Jellyfin does **not** use forced-IDR at all; for exactly these encoders it drops reliance on forced keyframes and fixes the GOP (`-g:v:0 N -keyint_min:v:0 N`, `EncodingHelper.cs:2040-2074`, comment "Unable to force key frames using these encoders, set key frames by GOP"). The first-pass audit suggested `-g`/`-keyint_min` as an additional bound; the lane left that out, which keeps the change minimal and is defensible.
- Findings:
  1. **Should fix (cheap hardening)** — `hardware.go:288-307` (`probeArgs`): the start-up encode probe does not pass the new option. The server can run a non-bundled FFmpeg (`PORTICO_FFMPEG`, or `PATH`; `mediatools/resolve.go:178-203`). With a build whose encoder lacks the option, the probe passes and then *every* conversion on that backend exits with "Unrecognized option", is re-run in software, and never trips the breaker in practice (see 0b796bb). Adding the same two-way switch to `probeArgs` makes such a build report the backend unavailable instead. All three options exist in the bundled 8.1.2, so this only matters for owner-supplied FFmpeg.
  2. **Nit** — the unit test asserts strings in the argument list; it cannot show that an IDR is produced. That is inherent; the device note covers it.
- Tests run: `TestConversionForcesHardwareIDRFrames` passes (it would fail on the base for the three backends; it also asserts software, VA-API and VideoToolbox carry neither spelling).
- Residual risk: real NVENC, Quick Sync and AMF runs. The lane's note (19 s clip with 10 s source GOP, inspect first packet flag and start time of each segment, decode each segment alone) is specific and would catch a wrong fix. Add one line to it: also confirm `ffmpeg` does not exit with an option error on the *oldest driver/FFmpeg pair* Justin intends to support.

### eb3f9bc — Reset encrypted records after confirmed Android Keystore key loss  (bug B-19.4)
- Verdict: **REJECT as written** (one blocker; the structure is sound and the fix to the blocker is small)
- What it does: before every record read/write, and once at launch through a new `prepareSecureRecords` bridge method, the Android store checks whether its Keystore key still exists. If the alias is absent while record files exist, or the key throws `KeyPermanentlyInvalidatedException`, it writes a durable "pending" marker, deletes the whole record directory, deletes the key entry, writes a "notice" marker and removes the pending marker. The next launch consumes the notice and shows "This sign-in has ended. Sign in again". Apple gets a no-op method of the same name.
- What is right: the reset is whole-store and fenced (pending marker checked first on every operation, so an interrupted clean-up is finished before anything new is written and old ciphertext is never mixed with a new key); damaged ciphertext, a wrong-type entry (`containsAlias` true but no `SecretKey`) and every exception other than permanent invalidation stay fail-closed; AES-GCM, AAD binding, no-backup location and read-back are untouched; the bridge contract is the same on both platforms (`prepareSecureRecords(): Promise<boolean>`); JavaScript awaits it before the installation identity is read.
- Findings:
  1. **Blocker — a transient Keystore failure wipes a healthy store on Android 11 and older.** `PorticoRecordStore.kt:144-148` treats `keystore.getKey(alias) == null && !keystore.containsAlias(alias)` as proof the key is gone (`:118-120` then calls `resetLostRecords()`). That inference is only safe on Android 12+ (Keystore2), where `getKey` returns null solely for `KEY_NOT_FOUND` and throws for every other error. On API 24–30 — which is this app's range (`minSdkVersion 24`) and covers **every Fire OS release** and most Android TV boxes — `AndroidKeyStoreSpi.engineGetKey` and `engineContainsAlias` are both built on `android.security.KeyStore.contains()`, which returns `false` when the binder call to the keystore daemon throws `RemoteException`/`ServiceSpecificException` or returns any code other than `NO_ERROR` (it logs "Cannot connect to keystore" and carries on). So a keystore daemon crash/restart, or a daemon-side I/O or state error, during *any* record read or write presents exactly as "alias absent"; the new code then deletes all records (sign-ins, installation identity, pinned server identities, queues) and, on its retry once the daemon is back, deletes the still-valid key as well. Before this commit the same event only made one read return "unreadable". This is my reading of the AOSP sources for those releases; I could not run it, but the consequence is unrecoverable so it should be treated as real until disproved on a device.
     Required change: do not act on a single "absent" observation. Either (a) prove the Keystore is answering before believing it — generate a throw-away key under a second alias, confirm `containsAlias(probe)` is true, delete it, then look for the real alias again, and reset only if it is still absent (any failure of the probe is "ambiguous": throw, do not reset); and/or (b) require the absence to be observed on two separate process launches (write a "suspected" marker first; reset only when a later launch sees absence again). (a)+(b) together cost a few lines. On API 31+ the current check can stay.
  2. **Should fix — the check runs on every operation and leaks a Keystore operation each time.** `recoverLostKey()` (`:115-128`) is called from every `read` and `write`: one extra `KeyStore.load` + `getKey`, and a `Cipher.init(DECRYPT_MODE, …)` that is never finished or aborted. Each `init` opens a Keymaster/KeyMint operation that stays open until the cipher object is garbage-collected or the service prunes it; slots are few on older TEEs. It also doubles the IPC cost of every record access on slow TV hardware, some of them on the main thread (`PorticoTopShelf`). The invalidation probe is also close to dead code: `KeyPermanentlyInvalidatedException` is raised for keys that require user authentication, and this key does not. Do the key check once per process (in `prepareSecureRecords` and lazily on first use), keep only the cheap `resetPending.exists()` test on the hot path, and drop or `doFinal`-guard the `Cipher.init` probe.
  3. **Should fix — a missing method silently disables device-bound sign-in.** `src/app/session.tsx:46`: `await NativeModules.PorticoRuntime.prepareSecureRecords()` sits inside the `try` whose `catch` swallows everything. If the method is absent (a development client with older native code, or any future runtime without it) the `TypeError` is swallowed and the installation identity is never set for that launch. Guard it (`typeof … === 'function'`) or give the preparation its own `try`.
  4. **Nit** — `session.tsx:269` builds the notice by concatenating two catalogue strings with a space (`…ended` + `…signInAgain`); that does not survive languages with different sentence order and the second string is a button label with no full stop. A dedicated string is the right fix (the lane notes it could not edit the shared catalogue).
  5. **Nit** — `mark()` fsyncs the marker file but not its directory, so after a power loss the marker's directory entry may be gone while some deletions persisted. The outcome is still safe (the next launch sees files without a key and resets again, or sees nothing and stays silent), just possibly without the one-time notice.
  6. **Nit** — `prepareSecureRecords` now creates the key at every first launch even if nothing is ever stored. Harmless.
- Tests run: `test/secure-store-recovery.test.ts` passes. It is a set of regular expressions over the Kotlin source (ordering of `mark`/`delete`/`deleteEntry`, presence of the `containsAlias` guard). It would not catch finding 1, and cannot.
- Residual risk: everything — Kotlin compilation, real Keystore providers, file durability, the notice UI. The lane's device note is thorough for the *intended* path (delete only the alias, corrupt a tag, interrupt the clean-up) and would catch a wrong happy path. ### e762b66 — Open auxiliary event streams through the verified server route  (bug B-22.18)
- Verdict: **ACCEPT WITH CHANGES** (one blocker in two constants; do not device-test before fixing it)
- What it does: replaces the raw-XHR stream opener with `openEventStream(api, path, headers, signal)`, which takes the destination from the API's own `RouteConnection` (resolve → confirm the snapshot is `ready` on that origin → dispatch in the same tick), closes itself on any route revision change, caller abort or reader release, and reads bytes through three new bridge methods (`openNetworkStream`, `readNetworkStream`, `cancelNetworkStream`) implemented with OkHttp on Android and a per-stream `NSURLSession` on Apple.
- Does it match the normal transport? I compared it with `RouteConnection.fetch` (`packages/client-core/src/route-connection.ts:136-163`) and `PorticoTransport`/`boundedRequest`:
  - **Route selection** — same source of truth (`route.resolve`), and slightly stricter: `fetch` re-resolves once if the snapshot moved, the stream opener throws and lets its owner retry. There is no `await` between the readiness check and the native dispatch (`event-stream.ts:37-41`), so no window in which the bearer can go to a superseded origin; the "late completion" case is fenced by `closed`. The tests drive exactly these races through the real adapter and are meaningful.
  - **Server-identity verification** — inherited, exactly as for ordinary requests: the origin is one that passed the nonce-bound identity proof against the pinned key; neither transport re-proves per request. TLS is the platform default validation in both (no custom trust handling was added).
  - **Redirect refusal** — Android: `followRedirects(false)`, `followSslRedirects(false)` and any 3xx is closed and rejected (`PorticoEventStream.kt:29,53-57`); stricter than the normal transport, which rejects only the five redirect codes that carry `Location`. Apple: `willPerformHTTPRedirection` answers `nil` and cancels, and `didReceiveResponse` also refuses 3xx. No follow-up request is issued on either platform.
  - Also narrower than the normal transport: GET only, and only `/v1/notifications/events` or `/v1/groups/<id>/events`; no cookies, no cache, no connection retry; four streams, 16 KB chunks, 1 MB per stream.
  - Bridge contract: same three methods, same argument order, same result shapes (`{status, headers}`, `{done, data?}`), same rejection code on both platforms.
- Native reading notes (no defects found in these): Android — non-local returns from `synchronized` are legal, `val entry` is assigned inside `synchronized` (allowed by its exactly-once contract), the dispatcher slot is released when `onResponse` returns so long streams do not occupy OkHttp's per-host limit, blocking reads run on a four-thread pool and never on the UI or bridge thread, cancellation from another thread unblocks the read by cancelling the call. Apple — the session retains its delegate, and both exit paths invalidate the session (`cancel` → `invalidateAndCancel`, completion → `finishTasksAndInvalidate`), so no retain cycle survives; delegate callbacks are serialised on a one-operation queue and all shared state is under `@synchronized(self)`; promise blocks are cleared after use so none is settled twice; module invalidation cancels this module's streams and any whose owner has been deallocated.
- Findings:
  1. **Blocker — the idle timeout equals the server's heartbeat, and a timeout is reported as a failure that invalidates the API route.** Both transports give up after 20 s without bytes (`PorticoEventStream.kt:31` `readTimeout(20, SECONDS)`; `PorticoPlayer.m` `timeoutIntervalForRequest=20`). The server heartbeats `/v1/notifications/events` every **20 s** (`portico-server/server/internal/httpapi/notifications_routes.go:425`; it even tells the client `"heartbeatSeconds": 20`), and before each heartbeat it runs an authorisation check, so the heartbeat arrives a little *after* 20 s of silence. An idle receiver stream therefore times out at essentially every heartbeat (always on Apple, where the timer runs from the last byte; a coin-flip on Android). A timeout before the 60 s lifetime is treated as a real failure on both platforms (`expired` is false), so the JavaScript reader calls `route.recover()` (`event-stream.ts:51-54`), which invalidates the verified route: phase goes to `probing`, origin to null, every other stream closes (revision changed), new API requests wait for a fresh identity probe, and `mediaURL()` returns an empty string until it completes. Then the stream reconnects and the cycle repeats about every 20 seconds for as long as a TV sits in receiver mode — including during playback. The group stream (15 s heartbeat) has only a 5 s margin.
     Required change: make the idle timeout comfortably longer than the slowest heartbeat on these two endpoints — 45–60 s — on both platforms, and keep them equal.
  2. **Should fix — the 60-second hard lifetime is an unrequested behaviour change that makes every stream reconnect once a minute.** `callTimeout(60, SECONDS)` / `timeoutIntervalForResource=60`. The server already bounds these streams at 30 minutes and tells the client to reconnect; the old adapter's only bound was 1 MB. With a 60 s cap, `GroupSessionService.connect` (`packages/client-core/src/group-session.ts:176-180`) publishes `phase: 'reconnecting'` and waits ~0.4–0.6 s before reopening, so a Watch Together room flips to "reconnecting" every minute; the receiver stream, which sends no `Last-Event-ID`, has a blind gap every minute and falls back to its slow poll; and on Apple each reopen is a new session and TLS handshake. If a wall-clock bound is wanted at all, set it just above the server's lifetime (for example 35 minutes); the 1 MB cap already bounds memory.
  3. **Should fix — local refusals also invalidate the route.** `event-stream.ts:62-66`: any rejection of `openNetworkStream` that is not caused by `close()` calls `route.recover()`. That is right for a connect failure, but the native side also rejects for "Too many event streams" (the four-stream cap) and "Invalid event request" (path not allow-listed). Neither says anything about the route; recovering on them closes the other streams, which reconnect, which can hit the cap again. Have the native side use a distinct code for local refusals and skip `recover()` for it.
  4. **Should fix (test note)** — the reader now hands `Uint8Array` chunks to `readEventStream`, which decodes with `new TextDecoder().decode(chunk, {stream: true})` (`packages/client-core/src/sse.ts`); the old adapter handed over strings and never touched `TextDecoder`. Route verification already uses a non-streaming `TextDecoder` on native, so the class exists, but **streaming decode on Hermes (react-native-tvos 0.83) is unproven** here. If it is unsupported, every event stream fails on first read. The device note mentions availability; it must specifically check a multi-byte character split across two chunks on each runtime.
  5. **Nit** — Apple `openNetworkStream`: `[NSURL URLWithString:url]` is called before the nil/length check on `url`; a nil argument from JavaScript would raise rather than reject. JavaScript never passes nil today.
  6. **Nit** — Android builds a second `OkHttpClient` with its own connection pool; `PorticoTransport`'s client could be the base (`newBuilder()`) so HTTP/2 connections are shared. Not required.
  7. **Nit** — on the 1 MB bound both platforms drop the final partial chunk rather than deliver it; harmless for the group stream (it resumes by id), a possible lost hint on the receiver stream, which its poll covers.
- Tests run: `test/event-stream-routing.test.ts` — 5 pass. Four of them exercise the real TypeScript adapter and the shared SSE parser against fakes (routing to the selected origin, no bearer without a verified route / cross-origin / pre-aborted signal, split UTF-8, both route races) and fail on the old adapter for the right reason. The fifth is a source-text guard on the native files; note that it *pins the defective constants* (`callTimeout\(60,` and `timeoutIntervalForResource=60`), so it must be updated with findings 1–2.
- Residual risk: both native implementations are uncompiled; real socket behaviour, cancellation while a read is blocked, JS reload, and the heartbeat interplay can only be seen on devices. The lane's device note is long and good on routing and redirects; add "leave a TV idle in receiver mode for five minutes and confirm the route snapshot's revision does not change and no identity probe is sent" — that single check would have caught finding 1.
