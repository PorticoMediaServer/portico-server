### b5da76a — Keep an active member's tier and libraries when they accept an invitation (bug B-13.21)

- Verdict: **ACCEPT WITH CHANGES**
- What it does: Applies an invitation's role/library template only to a newly created account or a disabled membership. An active member keeps the owner's current role, libraries and revision; acceptance still spends the invitation and journals consent in the same transaction as sign-in.
- Findings:
  1. **Blocker — `server/internal/access/invitations.go:485`: a pending invitation still undoes owner removal.** Create an admin/broad-library invitation, then disable or narrow an existing linked member through member management, then redeem that still-pending invitation as the disabled account. `disabled<>0` clears the disablement and installs the older invitation's role/libraries. This is an existing vulnerability left in the stated bug fix, not a new regression introduced by the active-member predicate. `identity/direct_accounts.go:724–734` treats disablement as membership removal and revokes credentials; `identity/portico_accounts.go:68` otherwise refuses that exact identity. Identity contract §1 separates authentication from local authorization, §6 requires removed membership to clear that server's credential, and Sharing/Social §4.1 says stale broader permission cannot override newer narrower authority. “Creates or returns” (§3.2.4) is not authorization to lift a suspension using an unrelated or older link. **Preserve disabled memberships and refuse this acceptance before spending the invitation or journaling it; require explicit owner re-enablement.** If automatic re-invitation is desired, Justin must approve a flow bound to that membership and its current revision. The shared disabled bit prevents distinguishing voluntary departure from suspension; it does not require failing open. Owner member management already provides a conservative recovery route without a schema change. Replace the restoration test with a pending-link-before-removal refusal test using the real sign-in callback, including an old admin invitation and removed libraries.
- Authorization trace: The active-member fix is correct in both directions. A member opening an admin invitation cannot gain admin/libraries; an admin opening a member invitation is not demoted. A member narrowed by the owner while still active cannot recover the removed libraries through an older invitation. The single writer transaction serializes member edits and acceptance; sign-in reads current membership rather than restoring the invitation's template later. Owner role stays excluded. Disabled restoration grants the invitation's access rather than the old membership's access, which avoids one escalation but does not protect removal. Unbound/password account creation and missing email binding are pre-existing adjacent gaps; they do not justify overriding a known removed identity. No full recipient-binding rewrite is requested in this pass.
- Tests run: `GOCACHE=/tmp/gocache-codex GOPROXY=off go test ./internal/access/ ./internal/hosted/ ./internal/social/ ./internal/downloads/ ./internal/persistence/` — all passed (access 6.425s, hosted 11.341s). `GOCACHE=/tmp/gocache-codex GOPROXY=off go test ./internal/httpapi/ -run 'TestSocial|Invit|Access|Portico'` — passed, 13.311s. The added active-member cases assert role, library set, revision, one linked account, spent invitation and consent journal. The disabled test deliberately asserts the unsafe restoration, so its pass is not evidence that removal is protected. Pre-fix failures are lane-reported, not independently rerun here.
- Residual risk: Hosted assertion/consent push and real-device sign-in were not exercised. Product contracts still describe Hosted-owned membership, whereas current architecture and implementation use server-owned membership; neither authority model permits identity proof alone to defeat current server removal.

### 1dae68b — Move an audiobook's resume point to the part last listened to offline (bug B-14.11)

- Verdict: **ACCEPT WITH CHANGES**
- What it does: Resolves a part to its book and creates/moves the book resume pointer when an accepted offline observation is newer than the current part's activity. Same-part updates preserve the existing writer binding; cross-part moves clear it. Films do not acquire book pointers.
- Findings:
  1. **Blocker — `server/internal/downloads/progress.go:241–259`: old activity does not date the current online pointer.** An online Start can move the book to part 5 at noon using its stored 900-second resume point, before its first progress report. `playback/personal_progress.go:67–74` updates the pointer/writer, but does not update `progress_activity`; that row can still reflect yesterday, or be absent. An 11:00 offline observation of part 3 then passes this comparison, moves the book backward, and clears the newly accepted online pointer's `playback_id`. Later part-5 telemetry cannot restore that pointer because the production catalogue writer updates it only for the matching item/writer (`catalog/personal_activity.go:141`). The new test helper seeds progress, activity and pointer together, hiding this production window. **Fence a move against the current bound occurrence's creation/activation evidence as well as current-part activity; ordinary new sessions already have indexed `playback_observations.created_at` from baseline trigger `playback_observation_create` (line 4107), so the ordinary Start case needs no migration.** Do not clear a pointer owned by a newer accepted online occurrence. Add a test that uses production online activation with absent/old activity, syncs an older different-part observation before first telemetry, and confirms both pointer and writer remain. Broader B-14.10 intent arbitration may remain deferred, but this new pointer move must not destroy an online pointer the old offline code left intact.
  2. **Should fix — `server/internal/downloads/progress.go:254`, interacting with existing line 212: subsecond ordering is lost across parts.** Offline activity is stored with `Format(time.RFC3339)` (whole seconds), whereas `SyncProgress`'s offline watermark is integer milliseconds. Receive part 5 at `12:00:00.900Z`, then part 3 at `12:00:00.100Z`: current-part activity reads `12:00:00Z`, so the older part-3 observation incorrectly wins. Reversing those two observations changes the final book pointer. An in-memory SQL probe using the exact SELECT/UPDATE/UPSERT strings from `followBook` produced part 3 at 300000 ms instead of part 5 at 900000 ms. **Compare against the current part's owner-scoped `download_progress_marks.observed_ms` as well as online activity, preserving at least the existing millisecond precision (or preserve equivalent precision in activity writes).** Add forward/reverse same-second cases and a retry in a separate batch; use the same stable viewer key as existing reconciliation, not an account/profile-only approximation.
- Ordering judgment: The normal later-online-progress case is protected: an earlier different-part observation can update that part's own progress without moving the book; an earlier same-part observation is rejected before `followBook` by `SyncProgress`. Whole-second, hour-separated offline observations are order-independent. **The stronger claim that no newer online pointer can move backward is false in the activation window, and cross-part offline ordering is not equivalent to the existing millisecond watermark.** Equal activity times conservatively preserve the current different-part pointer. Deliberate later seeks/replays may legitimately move a position or part backward; a numerical max-position rule would be wrong.
- Tests run: Downloads/persistence package tests above passed (8.861s / 33.628s), including all four added audiobook/film tests and statement guards. Vet/formatting passed. An inline Python/SQLite probe read the three new SQL statements directly from the Go source and used an isolated in-memory minimal fixture: reverse same-second observations moved to the wrong part; a genuinely newer online activity preserved part 5; a new online binding with only old activity allowed the old offline part to take over. This verifies the query/comparison behavior, not a full production Go playback reproduction. Production activation and its later update predicate were traced in source. Pre-fix test failures are lane-reported only.
- Residual risk: Native per-part outbox generation was not exercised. The pre-existing B-14.10 omissions (explicit personal fences, full history/completion policy and device event arbitration) remain; passing this lane's tests is not proof of full reconciliation conformance. Do not change those policies opportunistically in this fix. Lookups are primary-key/indexed and the pointer move shares the progress transaction, so no independent SQL race or new schema requirement was found.
