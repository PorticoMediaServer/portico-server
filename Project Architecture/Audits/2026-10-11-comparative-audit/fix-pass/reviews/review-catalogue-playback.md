### 50e71c8 — Keep derived step workers and rebuilds moving past an id that never derives (bug B-07.1)
- Verdict: REJECT
- What it does: Excludes in-memory poisoned entities from ordinary domain scheduling so secondary workers can run, then retries poison when other work is idle. Rebuild enumeration also skips poisoned entities and can clear the rebuilding flag with their durable dirty rows outstanding.
- Findings:
  1. **Blocker — `server/internal/compactcatalog/derive.go:365`: a failed rebuild is advertised as ready.** Once enumeration ends, `rebuilding=0` is committed even when a known failed entity still has rows from the old derivation version, or missing rows after a table was emptied. `CheckReadiness` (`:127`) checks only this flag, so readers receive a mixture without a building/degraded indication. The new test explicitly expects this behavior but uses a fake domain and never exercises a reader or version-incompatible rows. This pre-empts **D-14**, an open decision between waiting and serving old data; the current Catalogue architecture, “Derived data,” says readers wait until the domain catches up. Keep the readiness fence for an incomplete rebuild and schedule bounded secondary-worker turns independently of it. If degraded availability is wanted instead, it needs Justin's D-14 decision plus an explicit degraded contract and owner-visible diagnosis, not just a cleared flag. Logs identify an entity and domain but do not tell readers or the owner UI that a rebuild completed incompletely. Existing factual authorization checks mean this is not evidence of an access-control leak.
  2. **Should fix — `server/internal/compactcatalog/derive.go:351`: poison retries are not fair within a domain.** Retry always selects the lowest entity id. If two poisoned ids remain and the lower one never recovers, the higher one is never tried again, even after its source is repaired. Rows are durable and not deleted, but one entity can remain stale indefinitely. Rotate an in-memory retry cursor within each domain; add a two-poison test where only the higher id recovers.
  3. **Should fix — `server/internal/compactcatalog/derive.go:252`: poison-only scheduling can become quadratic.** The correlated `json_each` exclusion scans the entire all-domain poison list for each dirty candidate. An all-poison domain must visit all its dirty rows to prove the `EXISTS` false; the poison map is unbounded. Precompute a membership set/subquery per domain or otherwise avoid repeated linear JSON scans. The per-item guard explicitly exempts statements containing `FROM catalog_derivations st`, so its passing result does not establish this query's bounded cost.
- Tests run: `GOCACHE=/tmp/gocache-codex GOPROXY=off go test ./internal/compactcatalog/... ./internal/persistence/... ./internal/decoder/... ./internal/lyrics/... ./internal/subtitles/... ./internal/dbwork/...` — PASS, including both new failure tests and statement guards. The test demonstrates durable retention and secondary-worker progress, not safe degraded reads or fair retries.
- Residual risk: The real worker's five-second error delay is interrupted by shared commit signals, floored to one second by `worker.RunWith`; `setAside` updates `catalog_derivations` and can wake its own loop. Thus this is not a zero-delay hot loop, but the report's “every five seconds” is not guaranteed (pre-existing). A supervised-loop/backoff test is still needed for operational cadence.

### efdb847 — Keep a presentation's quality ceilings when a subtitle burn-in re-plans it (bug B-02.12)
- Verdict: REJECT
- What it does: Stores the effective v1 `QualityTarget` inside the existing policy JSON and reuses it for burn-in on/off, across v1 PATCH and legacy subtitle-selection routes. It also carries that target onto a copy-timeline fallback plan.
- Findings:
  1. **Blocker — `server/internal/playback/subtitle_delivery.go:44`: old v1 rows still lose ceilings.** An old `policy_json` has no `sessionTarget`, so `old.Target == nil` enters the legacy rung fallback. `quality_id='original'` resolves to `QualityRung.Target` (`quality_ladder.go:177`), which sets every ceiling to zero; `quality_id='limit'` still returns `ErrQualityUnavailable`. Reading old JSON is compatible, but replanning it is not safe or functional. Existing active rows were explicitly required to be considered, and no migration invalidates them. Recognize old v1 presentations via their stored v1 request/media association and reconstruct a conservative admitted target, or refuse a replan when the original ceilings cannot be recovered. Do not treat absence as authorization for uncapped original. Add old-flat-policy tests for original/member-cap and limit sessions, including burn-off and unknown JSON fields.
  2. **Blocker — `server/internal/playback/hls_produce_support.go:179`: copy-timeline fallback still ignores the stored target.** `downgradeCopyPlan` plans with `rung.Target(policy,height)` and only assigns `next.Target=plan.Target` after planning (`:189`). A v1 original stream that was eligible for copy under a low bitrate ceiling can become an 8-Mbit/s conversion when indexing fails, although the stored session ceiling is lower. A v1 limit stream fails rung lookup instead. The lane disclosed this, but it is an active replan and the modified file carries the very field needed to fix it. Use the stored target when present, with the same conservative old-row handling; test capped copy → conversion fallback and the subsequent burn-on/off.
  3. **Should fix — `server/internal/playback/subtitle_delivery.go:41` and `server/internal/playbackv1/sessions_change.go:118`: current admission is not intersected with the frozen target.** Subtitle-only changes do not call `c.admit`, unlike other changes that produce new bytes. A LAN-started presentation changed remotely retains no original remote member ceiling; lowered owner ceilings in the current `cfg` are also not intersected into `target`. Preserving the original target is necessary, but a current stricter applicable ceiling must only narrow it. Re-admit subtitle byte changes without double-counting the existing stream, intersect current member/owner limits with the stored target, and cover the legacy subtitle PUT route too. Add tests for a reach change and tightened settings. This limitation is acknowledged in the lane report, but no contract explicitly exempts newly generated bytes from current ceilings.
- Tests run: Full playback/playbackv1 suites PASS; exact command/results below. Focused HTTP subtitle/playback tests PASS. The added test covers two newly created v1 targets through direct callback calls, not old rows, owner height/audio ceilings, header manipulation, authorization of a different resource, or copy-timeline fallback.
- Residual risk: Real encoded bitrate and device burn-in are unverified. For **newly stored** targets, the trust trace is sound: client bodies contain quality requests only; remote classification and member cap come from server admission (`httpapi/playback_v1_routes.go:182`), owner limits come from configuration, and `Target` is `json:"-"` on the exposed plan. Subtitle request fields cannot write it. `sessionTx` ties session to principal/item/pinned asset, and selection ties resource to that source and revision. Changing headers, omitting subtitle fields or selecting another allowed resource does not enlarge that stored target. These checks do not solve the missing-target/fallback findings above.
