# Lane: native-platform

### 2cf810c — Preserve secure records when Android key absence is ambiguous  (bug B-19.4)
- Verdict: **NEW PROBLEM** (the round-one blocker is resolved in logic; the commit does not compile; and the outcome on Android 7–11 / Fire OS needs Justin's decision)
- What it does: on Android 11 and older, "key absent while record files exist" now throws and deletes nothing; only Android 12+ (where absence is an explicit not-found answer) and an explicit `KeyPermanentlyInvalidatedException` still trigger the whole-store reset. The key check runs once per process and completes its cipher operations. The reset marker is versioned, written by rename, and the parent directory is fsynced. A new guard refuses to generate a replacement key while record files exist. JavaScript calls the preparation method only if the runtime has it.

- Findings:
  1. **Blocker — the file does not compile.** `PorticoRecordStore.kt:171`: `OsConstants.O_DIRECTORY` is not part of the public Android SDK. `javap` on `platforms/android-36/android.jar` lists `O_ACCMODE, O_APPEND, O_CLOEXEC, O_CREAT, O_DSYNC, O_EXCL, O_NOCTTY, O_NOFOLLOW, O_NONBLOCK, O_RDONLY, O_RDWR, O_SYNC, O_TRUNC, O_WRONLY` and nothing else; the Kotlin 2.1.20 compiler reports `PorticoRecordStore.kt:171:102: error: unresolved reference 'O_DIRECTORY'`. The Android app cannot be built from this branch. Fix: `Os.open(path, OsConstants.O_RDONLY, 0)` — opening a directory read-only and calling `fsync` on it is valid on Linux without that flag. I compiled a scratch copy with only that token removed: it compiles clean, so this is the only compile error in the file. The lane's source-text test pins `Os.fsync(descriptor)` and cannot see this.
  2. **Decision for Justin (Should fix before release) — on Android 7–11 and every Fire OS TV release, a genuinely lost key now leaves the app permanently unable to save anything, and sign-in no longer works at all.** Traced precisely:
     - Every launch: `prepareSecureRecords` → `recoverLostKey` → key absent, records exist, API < 31 → throws (`:125`). The bridge rejects; `session.tsx:45-50` swallows it, so no installation identity is set for that launch.
     - Every read returns "unreadable" (the throw is caught in `read`). Every write returns false, **including removals**, because `recoverLostKey()` runs before the delete branch (`:78`). `keyChecked` never becomes true in this state, so each operation repeats the Keystore lookup and directory walk.
     - Nothing is ever deleted, so `hasRecords()` stays true for ever, and the new guard `check(!hasRecords())` (`:181`) means no replacement key is ever generated.
     - Sign-in: `ViewerSelectionCommit.commit` reads the saved selection first; that rejects ("could not be read"), or, once the quarantine flag is set, the save is refused ("The server credential could not be saved"), the rollback write also fails, and the user sees "The profile change could not be rolled back safely…". Either way the sign-in is not kept.
     - So the answer to "stuck for ever, in a loop, or able to sign in again and overwrite?" is: **stuck signed out for ever; no delete loop; cannot overwrite.** The only way out is clearing the app's storage in system settings, or reinstalling. There is no message telling the user that.
     - This is *harsher than the code before the lane started*: the audit entry records that a plain save used to create a new key, so sign-in succeeded and the user was re-prompted about every 15 minutes. The new guard removes that. (The guard is right in itself: it closes a pre-existing hazard where a transient "absent" answer followed by key generation would overwrite a healthy key and orphan every record. But its cost is this lock-out.)
     - Net effect: B-19.4 is fixed on Android 12+ only. Fire TV (Fire OS 6/7/8 = API 25/28/30) and most Android TV boxes are below that, so for most of the television fleet the bug is still open and more visible.
     - Options, none of which the lane could choose alone: (a) accept, and add a plain message that says to clear the app's storage (new copy needed); (b) a user-confirmed reset — when preparation fails with this specific reason, offer "This device's saved sign-in can't be read. Reset it and sign in again", which calls an explicit native reset (the user's consent replaces the proof the platform cannot give; worst case is one extra sign-in and lost offline queues); (c) automatic reset on API < 31 only after strong evidence: a throw-away key round trip immediately before *and* after the "absent" observation, seen on two or more separate launches. I recommend (b), optionally with (c)'s evidence as a precondition for showing the offer. The bridge would need a distinct rejection code for "key cannot be verified" (today everything is `secure_storage`).
  3. **Nit** — `:47-48`: launch preparation verifies the key twice (`recoverLostKey` → `verifyKey(existing)`, then `verifyKey(key(create = true))`): four Keystore cipher operations and two `KeyStore.load` calls on every launch. One is enough; skip the second when `recoverLostKey` already verified.
  4. **Nit** — an old one-byte marker left by the rejected implementation blocks the store for ever (every operation throws at `:150`). That implementation never shipped and never compiled into a release, so only a developer device could have one; say so in a comment, or treat an unrecognised marker as "delete the marker, do not reset".
  5. **Nit** — on Android 12+ the reset can run on whichever thread first touches the store. `PorticoTopShelf` reads on the main thread, so a one-time reset (recursive delete, four directory fsyncs, key generation) can happen there. One-off; acceptable.
  6. **Nit** — the round-one string nit (two catalogue strings joined with a space, `session.tsx:269`) is still open; the lane says why.

- The questions put to this review, answered:
  - **Can any transient or service failure still delete records?** By reading, no.
    - API 24–30: deletion needs either a valid `confirmed-key-loss-v2` marker (only ever written after proof) or a caught `KeyPermanentlyInvalidatedException`. A failing Keystore service on these releases shows up as `getKey` → null and `containsAlias` → false (now: throw, delete nothing), or as `ProviderException` / `KeyStoreConnectException`, a plain `InvalidKeyException`, or `UnrecoverableKeyException` — none of which is the caught type. `KeyPermanentlyInvalidatedException` is only constructed from specific response codes returned by a working daemon (user-authentication codes with no usable authenticator, and on some releases "uninitialised"), which apply to authentication-bound keys; this key is not one. Residual: a vendor Keymaster that returns such a code spuriously for a non-bound key. I regard that as remote; round one judged the same path "close to dead code".
    - API 31+: `getKey` returns null only when Keystore2 answered `KEY_NOT_FOUND` after a completed call; binder failures are retried once and then thrown as a system error. Residual: Keystore2 itself answering not-found for a key that exists (for example during the one-time legacy import after an Android 11→12 upgrade). I know of no transient case; if it happens the key is in practice gone.
    - The app is single-process (no `android:process` in the manifest) and every store entry point holds the store lock, so no second writer can observe a half-finished reset.
  - **Is the fencing correct across process death at every step?** Yes. Walk-through: (1) marker written to `.new`, fsynced, renamed, directory fsynced — a crash before the rename leaves no marker and the next launch re-derives the proof from scratch; (2) recursive delete — a crash leaves the marker, and every later operation re-enters the reset before doing anything else; (3) parent fsync; (4) key entry deleted — a crash here resumes, finds no records and no key, continues; (5) new key generated and round-tripped — the `check(!hasRecords())` guard is satisfied because the directory is gone; (6) notice written; (7) marker removed and directory fsynced. A crash between (6) and (7) repeats an empty reset (deletes the just-created, unused key, makes another, rewrites the notice) — harmless, and the notice is still shown once. No step can publish a record between the marker and its removal, because the reset runs to completion inside the lock. Two very small holes, both needing a second fault: the removal of the consumed *notice* is not directory-fsynced (a power cut can show the note twice), and if the final directory fsync itself throws, the marker removal may not be durable until the next journal commit (a power cut inside that window after a new sign-in would redo the reset). Neither is worth a change.
  - **Does the app recover once, cleanly, where loss can be proven?** Yes on Android 12+: first launch after the loss wipes the store, creates and verifies a new key, returns `true` once, JavaScript shows the "sign-in has ended, sign in again" note once, and subsequent launches are normal. Interrupted resets finish on the next operation.
  - **Android 7–11 and Fire OS:** see finding 2.
- Round-one findings: 1 (wipe on ambiguous absence) resolved; 2 (check on every operation, unfinished cipher) resolved; 3 (missing method disables installation identity) resolved in `profile-trust.ts` with a real test; 5 (marker directory durability) addressed, by the line that does not compile.
- Tests run: `npm test` 258/258 (the three recovery tests pass; two are source-text guards, one exercises the real TypeScript bridge helper with the method absent, resolving and rejecting). Standalone Kotlin compile: fails on `:171` as above; passes with that token removed.
- Residual risk: real Keystore providers, real file durability, the notice UI. The lane's revised device note is specific and would catch a wrong fix; add "the Android app builds" as step zero, and add the user-visible check for finding 2 (after deleting only the alias on an API ≤ 30 device: can the person sign in? what do they see?).

### 11f27fe — Keep idle auxiliary streams from invalidating verified API routes  (bug B-22.18)
- Verdict: **RESOLVED WITH NITS**
- What it does: idle timeout 20 s → 60 s and hard lifetime 60 s → 2100 s on both platforms; native rejections now carry one of five codes (`event_timeout`, `event_local`, `event_redirect`, `event_cancelled`, `event_transport`) and the TypeScript adapter asks for route recovery only on `event_transport`. Apple validates the URL and identifier arguments before building an `NSURL`.
- Checked against the server (read-only checkout):
  - `/v1/notifications/events`: heartbeat ticker 20 s (`notifications_routes.go:425`, announced as `heartbeatSeconds: 20` at `:412`), preceded by a strict authorisation check; lifetime 30 minutes (`:53`), ended with a `closed` event.
  - `/v1/groups/{id}/events`: heartbeat 15 s (`social_routes.go:454`), lifetime timer 30 minutes (`:551`), ended by returning.
  - Client: 60 s without bytes is three missed heartbeats on the slower stream and four on the faster; 35 minutes is above the server's 30. Both platforms use the same two numbers. The server always ends the stream first, so the client lifetime only matters against a misbehaving peer; when it does fire, Android resolves `{done: true}` (elapsed ≥ 2 100 000 ms is guaranteed because the entry's start is taken before the call timer starts) and Apple likewise (≥ 2099 s). If a clock quirk made either test false the result is `event_timeout`, which also does not touch the route.
- Route selection, identity and redirects: the adapter's sequence is unchanged — `route.resolve` → snapshot must be `ready` on that origin → revision captured → native dispatch in the same tick; a revision change, caller abort or reader release closes the stream. Redirect refusal is unchanged on both platforms (OkHttp follow-ups off and any 3xx rejected; `willPerformHTTPRedirection` answers nil and 3xx responses are cancelled) and now reports `event_redirect`. Path allow-list, four-stream cap, 16 KB chunks and 1 MB bound are untouched.
- Cancellation and reconnect, both platforms:
  - Android: `cancel(id)` removes the entry, cancels the call and closes the response; a read blocked on the socket is released by the call cancel and is reported `event_cancelled` (new `entries[id] !== entry` test under the lock). A cancel that lands between enqueue and response is caught by the identity check in `onResponse`, which closes the response. Reader pool is a fixed four threads with at most one read per entry and at most four entries, so it cannot grow or starve; the worst case for a blocked reader is now 60 s rather than 20 s. No new thread or connection is created per reconnect beyond the one call.
  - Apple: `cancel` invalidates-and-cancels the per-stream session; normal completion calls `finishTasksAndInvalidate`; either releases the delegate. Promise blocks are cleared after use. `failureCode` is only written inside `@synchronized(self)`.
  - JavaScript-initiated closes during open are still guarded by `closed`, so the Android "Canceled" `IOException` (which maps to `event_transport`) cannot trigger recovery.
- Findings:
  1. **Should fix (small)** — a timeout *while connecting* is now also classed `event_timeout` and no longer asks for recovery. Android `PorticoEventStream.kt:51`: `SocketTimeoutException` from the 15 s connect extends `InterruptedIOException`; Apple `PorticoPlayer.m:255`: `NSURLErrorTimedOut` before any response. A black-holed route (the usual way a LAN route dies when the device leaves the network) is route evidence, and round one said recovery "is right for a connect failure". Ordinary API requests still recover the route on any thrown error (`route-connection.ts`, `fetch`), and receiver and group modes send regular heartbeats, so this is a lost signal rather than a stuck state. Make the code `event_transport` when the timeout occurs before response headers (Android: in `onFailure`; Apple: when `openingReject` is still set) and keep `event_timeout` for idle reads.
  2. **Nit** — Apple's open now takes up to 60 s to fail against an unreachable host (the request timeout covers the connect), Android 15 s. Harmless, slower reconnect on Apple.
  3. **Nit** — with the lifetime at 35 minutes, a stream whose JavaScript owner stops reading without closing holds one of the four slots for up to 35 minutes instead of one. The adapter always reads or closes, so this is theoretical.
  4. **Nit** — Android maps a non-`IOException` during a read to `event_local`; fine, noting that an unexpected runtime error is then silent to the route.
  5. Round-one nits 6 and 7 (separate OkHttp pool; final partial chunk at the 1 MB bound) are unchanged, as the lane says.
- Round-one findings: 1 (blocker) resolved; 2 (60 s lifetime) resolved; 3 (local refusals invalidate the route) resolved; 4 (streaming `TextDecoder` on Hermes) is a device check and is now in the note; 5 (nil URL) resolved.
- Tests run: `test/event-stream-routing.test.ts` 7 pass. The two new tests drive the real adapter: four non-transport codes at open and at read cause zero recoveries, `event_transport` causes exactly one; both fail on the previous adapter. The constants test now pins 60 / 2100 on both platforms.
- Residual risk: device behaviour of both transports; that the rejection `code` survives the bridge on this React Native version (the app already relies on it elsewhere, `server-connections.ts:113`; if it did not, the failure direction is "never recover", which is the safe one). The lane's five-minute idle receiver check is the right acceptance test.

### 70f32a5 — Preserve startup engine fallback and separate HTTP delivery failures  (bug B-20.6)
- Verdict: **NEW PROBLEM** (no blocker; round-one finding 1 resolved, finding 3 resolved on Android, finding 2 only partly, and the Apple classifier gained mis-classifications that can turn a connection drop into a hard failure)
- What it does: both platforms now publish `httpStatus`, `deliveryError` and `hasPlayed` with an error. One TypeScript function decides: a known HTTP status wins (5xx/408/429 → network recovery, other 4xx → plain failure); otherwise delivery → plain failure; otherwise network → recovery; otherwise an explicit decoder/parser code → reported fallback; otherwise, **only if nothing has played yet**, `source_not_supported` → reported fallback; otherwise plain failure.
- Line-by-line comparison of the two native classifiers as they stand:

  | Condition | Android (`PorticoPlaybackController.kt:1005-1012`) | Apple (`PorticoPlaybackController.m:434-453`) | Same? |
  |---|---|---|---|
  | Source of HTTP status | `InvalidResponseCodeException` within four causes (structured, reliable) | `NSHTTPURLResponse` in `userInfo`; a regular expression over description / failure reason; CoreMedia −12938 → 404, −12660 → 403; then the item's **last error-log entry** (comment text, or a 400–599 status code) | Best effort on Apple |
  | 5xx / 408 / 429 with status known | network | network | Yes |
  | 5xx with no status recoverable (progressive play typically reports `NSURLErrorBadServerResponse`) | n/a (status always known) | `NSURLErrorBadServerResponse` is in the "permanent" list → delivery → plain failure | **No** |
  | 403 / 404 / 410 | delivery | delivery (−12938, −12660, `FileDoesNotExist`, `NoPermissionsToReadFile`, or status text) | Yes, when recognised |
  | Connection failed / timed out | `IO_NETWORK_CONNECTION_FAILED`, `_TIMEOUT`, `IO_UNSPECIFIED` → network | any non-"permanent" `NSURLErrorDomain` code in four levels → network, **unless any level also sets delivery, which then forces network off** (`:452`) | **No** |
  | POSIX errors | n/a | seven listed codes → network; **every other POSIX code → delivery** (`:445-447`) | Apple only |
  | HLS transport failures that carry only a CoreMedia code (segment time-outs and similar) | network (they are I/O codes) | unclassified → before first frame: reported as `source_not_supported`; after: plain failure | **No** |
  | File missing / no permission / cleartext / wrong content type / read out of range | delivery (five codes) | delivery (URL file codes, Cocoa file codes, ATS, `AVErrorContentIsUnavailable`) | Yes |
  | Behind live window | delivery | no equivalent | — |
  | Explicit decoder | eight codes → `decode_error` | three codes → `decode_error` | Yes in kind |
  | Explicit parser | four codes → `source_not_supported` | three codes → `source_not_supported` | Yes in kind |
  | Explicit decoder code **and** an HTTP status | status only from the same exception chain | status may come from an older, unrelated error-log entry and suppresses the decoder code | **No** |
  | Unclassified, nothing played | `source_not_supported` (JS) | same | Yes |
  | Unclassified after playback | plain failure, nothing learned | same | Yes |

- Findings:
  1. **Should fix — on Apple, deeper "delivery" evidence overrides "network" evidence, and the POSIX rule is a catch-all.** `:445-447` marks every POSIX error not in a list of seven as delivery, and `:452` (`else if(delivery)network=NO`) then cancels a network verdict from another level. Ordinary transport errors outside the list — `ECONNABORTED` (53, the classic error after an app returns from the background), `ENOTCONN` (57), `EPROTO` (100, HTTP/2 and QUIC), `ENOBUFS`, `EHOSTDOWN`, `ENETRESET` — would turn "connection lost, reconnecting" into "This media could not be played" with no retry. Before this commit any `NSURLErrorDomain` error in the chain meant network. Change: let only a short list of file/permission POSIX codes (`ENOENT`, `EACCES`, `EPERM`, `EISDIR`) mean delivery and treat the rest as network (or leave them unflagged); and resolve conflicts by level — the outermost classified error wins — rather than "delivery beats network".
  2. **Should fix — `NSURLErrorBadServerResponse` should not be in the permanent list** (`:442`). AVFoundation maps 404 and 403 to their own URL codes; what is left for "bad server response" is mostly 5xx. With no status recoverable (the error log exists for HLS, not for progressive playback), a 503 during direct play is a plain failure on Apple and a reconnect on Android — the same disparity round one reported, reversed. Treat it as network unless a status says otherwise. This is from my knowledge of how AVFoundation reports these; confirm with a captured error on a device.
  3. **Should fix — the error-log lookup can pick up a stale entry and it outranks everything.** `:436` reads `errorLog.events.lastObject` for the item. That log accumulates non-fatal events over the item's life (a variant that returned 404 once and was skipped, a 503 that was retried). If the item later fails for a real decoder reason, the old status is found, JavaScript's first rule lets a status win, and the decoder fallback is suppressed (old 404 → plain failure) or playback enters route recovery (old 503). Use the log entry only when the top-level error is not an explicit decoder/parser code and the entry is recent (its `date` within about 15 s).
  4. **Should fix — use the error log's domain as well as its text.** Apple still does not meet the audit's "treat every I/O-class error as network" for HLS failures that arrive as CoreMedia codes with no URL error in the chain. `AVPlayerItemErrorLogEvent` has `errorDomain` and `errorStatusCode`; when the domain is `NSURLErrorDomain` the code can go through the same network/permanent table. Without this, such a failure before the first frame is now *reported to the server as `source_not_supported`* — the original defect (a transport error closing a route for seven days), for the start-up case. Also consider allowing the word "response" in the status pattern (`:29`); I recall, but could not confirm here, that CoreMedia words some 5xx comments as "unrecognized http response NNN", which the pattern does not match.
  5. **Should fix (small) — exclude known non-format conditions from the start-up rule.** With "unclassified before first frame ⇒ `source_not_supported`", an interruption during start-up is taught to the server as an incompatibility: on Apple `AVErrorMediaServicesWereReset`, `AVErrorOperationInterrupted`, `AVErrorSessionWasInterrupted`, out-of-memory; on Android `ERROR_CODE_TIMEOUT`, `ERROR_CODE_REMOTE_ERROR`. Give these the plain-failure path (no report) on both platforms. The rule itself is what the audit and round one asked for; this only trims its false positives.
  6. **Nit** — `hasPlayed` is reset on every reload, including the reload after route recovery, so an unclassified error right after a network recovery on a title that had been playing for an hour is reported as an incompatibility. Keep the flag across a `routeResume` reload of the same source.
  7. **Nit** — Android crossfade: when an incoming deck is promoted (`:729`) `load` is not called, so `hasPlayed` stays true from the previous track and the start-up rule never applies to the promoted one. Music only; explicit decoder codes still fall back.
  8. **Nit** — `NSURLErrorDataNotAllowed` (cellular data off) is "permanent" on Apple; the Android equivalent is a connection failure (network). Either is defensible; pick one.
- Round-one findings: 1 (fallback lost) resolved on both platforms; 2 (platforms disagree on HTTP errors) resolved where a status is known, not otherwise (findings 1–4); 3 (permanent conditions shown as "Reconnecting" for 90 s) resolved on Android, best effort on Apple. The UI question the lane raises (what a permanent media error should look like) is still Justin's.
- Tests run: `test/playback-error-classification.test.ts` 2 pass — real tests of the TypeScript policy (status parity for seven statuses with conflicting native flags; start-up fallback; no learning after playback; network and delivery suppress engine codes). `test/playback-failure-policy.test.ts` passes (source-text guards). Nothing tests the native classification itself, and nothing could here. Kotlin hunk type-checks against Media3 1.10.1.

### 549b3d3 — Retry transient subtitle rechecks before the existing grant expires  (bug B-20.13)
- Verdict: **RESOLVED WITH NITS**
- What it does: after a transient recheck failure (transport error, truncated body, 5xx) both renderers back-date the last-request time by 20 s, so the 25-second cadence fires again 5 s later. Denials and invalid documents keep the normal cadence and still clear at once. No failure extends the 40-second authorisation deadline.
- Traced: Android `finished()` sets `lastRequest = now − 20 000` only on `answer == null || answer.transient`; the 1-second ticker starts a new fetch only when no call is in flight, so retries are sequential. Apple: `_transientFailure` is set only on the 5xx branch and cleared at each `fetch`; the completion applies the short retry when `_transientFailure || (!_failed && error)`. Terminal paths (non-200, wrong MIME, oversize, refused redirect which arrives as a 3xx response) have `_failed` set and `_transientFailure` clear, so they do not get the short cadence even though cancelling the task produces an error object. A superseded response is still dropped by the generation / task identity check before any of this runs.
- Timeline: success at 0, prompt failure at 25, retry at ~30 (and ~35 if needed), grant ends at 40 — round one's ten-second gap is gone for prompt failures. A recheck that hangs to its 15-second time-out still ends at 40 with a short gap; the lane says so and it is the correct trade against extending authority.
- Findings:
  1. **Nit** — the 5-second cadence continues for as long as the failure does, including after the grant has lapsed and when there were never any cues (initial load). During a server-side 5xx episode every viewer with app-drawn subtitles asks five times as often as before. Fall back to the 25-second cadence once `authorizedUntil` has passed.
  2. **Nit** — the "Subtitles could not be read" status is still raised while cues are on screen, now up to three times before the deadline (round-one nit, owned by the other native lane).
- Tests run: `test/subtitle-recheck-policy.test.ts` passes (source-text guards for the back-dating line on both platforms). Kotlin hunk type-checks.
- Residual risk: timers and rendering on devices; the lane's note is specific (expect the retry at t ≈ 30–31, continuous cues past 40 on success, 5-second spacing with no parallel requests, immediate clear on denial).

### df2f4e2 — Count hardware failures after productive software retries  (bug B-03.6)
- Verdict: **RESOLVED**
- What it does: the software re-run of a failed hardware window now confirms the hardware failure when it either exits cleanly, or was stopped by the throttle after publishing at least one segment beyond everything that existed before the retry. A viewer cancel, a superseded window, a failed software run or a throttle on old output does not count.
- Traced in `hls.go:563-611`:
  - `beforeRetry` is the higher of the on-disk contiguous edge and the window's recorded progress, read after the hardware child has exited and its watcher has stopped, so leftover hardware segments (or older segments at the same indices) cannot be mistaken for software output. Because the muxer writes segments in order from `from`, `produced > before` can only become true once software has encoded past all of that earlier output.
  - `retryCancelled := ctx.Err() != nil || !currentWindow || processCtx.Err() != nil && !softwareThrottled` parses as intended (`&&` before `||`): session cancelled, or window replaced, or the process context ended for a reason other than the throttle (including the six-hour cap).
  - Window fields are read under `h.mu` after `<-watchDone`; no new goroutine, lock order unchanged.
- The three questions:
  - **Opens for a genuinely failing GPU within a reasonable number of failures?** Yes: one count per session whose software retry gets one throttle buffer ahead of the viewer (default 60 s) or finishes; three counts inside ten minutes open the circuit (`toolchain.go:208-222`, unchanged). Sessions abandoned in the first seconds, and hosts whose CPU cannot get ahead of real-time playback, do not count until the title ends — acceptable, and far from "almost never".
  - **Not tripped by a few bad files?** Files that fail in software too never count. A file that only the hardware path rejects (and software converts) does count, once per *session*; three such sessions in ten minutes open the circuit for at most ten minutes, after which a clean re-probe restores hardware. That is inherent in a per-backend breaker with no per-title memory and was already true before this lane; it is bounded and self-healing.
  - **Cannot flap?** Opening needs three confirmed failures in a sliding ten-minute window; closing needs the window to pass *and* a successful re-probe; a failed re-probe re-arms the full cool-down. The fastest possible cycle is therefore three failed hardware starts per ten minutes, each of which the viewer experiences as a restart in software. No rapid toggling is possible.
- Findings: none requiring change.
  1. **Nit** — the table test covers the pure rule only; the capture of `beforeRetry` and the window check in `produce` have no test. A focused test would need a fake converter; not worth blocking on.
- Tests run: `TestHardwareFailureRequiresSuccessfulUninterruptedSoftwareRetry` (12 rows, including "throttled after output" → true, "throttle on old hardware output" → false, "viewer canceled after output" → false) and `TestSoftwareFallbackDoesNotDisableHardwareBeforeRetrySucceeds` pass; full `./internal/playback/...` passes; decoder breaker threshold / cool-down / re-probe tests pass.

### a5607db — Qualify forced IDR options in hardware encoder probes  (bug B-03.1)
- Verdict: **RESOLVED WITH NITS** (does what round one asked; the detection is narrower than the report claims, and never worse than before)
- What it does: the start-up encode probe (both the plain and the native-filter variants) now passes `-forced-idr 1` for NVENC and `-forced_idr 1` for Quick Sync and AMF, the same options production adds.
- Does a rejecting encoder now fail at probe time and fall back safely? **Only when the whole FFmpeg build does not know the option name.** I checked FFmpeg's behaviour with the local 8.0.1:
  - an option name no codec defines → `Unrecognized option … Option not found`, exit 8, before any device is touched. The probe now fails (`probe_encode_failed`), the verdict is cached in memory for that binary, `auto` moves to the next backend and otherwise software is used from the first session. That is the safe fallback round one wanted.
  - an option name that *another* codec in the build defines → FFmpeg prints a warning ("has not been used for any stream") and **exits 0** (`ffmpeg … -c:v mpeg4 -forced_idr 1 …` → exit 0; same for `-forced-idr`). The probe passes — and so does production. The option is silently ignored and the encoder does not force IDR frames.
  - Consequences: (a) for NVENC the added option can never make the probe fail in a build Portico can use, because `libx264` (a required encoder) defines `forced-idr`; (b) for AMF, a build whose Quick Sync encoders define `forced_idr` but whose AMF encoder does not passes the probe and runs production with keyframes that may not be IDR — B-03.1 silently unfixed on that owner-supplied build; (c) round one's premise that such a build makes "every conversion exit with Unrecognized option" was itself only true for the first case.
- Is anything disabled that would otherwise have worked? No. Where the probe now fails, production (since 890e7cf) would have failed on the same parse error in every session, so nothing working is lost; the change removes a failed hardware start per session. Compared with the code before 890e7cf, an owner-supplied FFmpeg too old to know `forced_idr` at all loses Quick Sync / AMF and runs in software — a deliberate fail-closed choice over producing segments that do not start independently. The bundled FFmpeg 8.1.2 has all three options. The reported reason is the generic `probe_encode_failed`; the owner is not told it was the option.
- Findings:
  1. **Should fix (low priority) or correct the claim** — to really qualify the option, read the encoder's own option list once per binary (`ffmpeg -hide_banner -h encoder=<name>` contains `forced-idr` / `forced_idr`), alongside the existing toolchain facts; no GPU needed. Until then the report should say the probe catches builds that do not know the option name at all, not encoders that lack it.
  2. **Nit** — `TestHardwareProbeRejectsUnsupportedForcedIDROption` simulates a rejection that real FFmpeg cannot produce for NVENC (see (a)); it tests the detector's plumbing, not FFmpeg's behaviour. On Linux it picks NVENC first.
- Tests run: `TestHardwareProbeQualifiesForcedIDROptions` (all five backends, both probe variants; asserts VA-API and VideoToolbox get neither spelling) and `TestHardwareProbeRejectsUnsupportedForcedIDROption` pass; full `./internal/decoder/...` passes. Local FFmpeg experiments as described.
- Residual risk: real NVENC / Quick Sync / AMF runs with the oldest FFmpeg Justin intends to support; the lane's note asks for the `-h encoder=` capture, which is the right evidence.
