### B-13.5 — Members who disappear stay in a group forever; the lobby shows everyone as "away"
- Status: SKIPPED (needs a migration and one product decision). Verified real.
- What I found: (a) the only writer of `state='left'` is `Leave` (`internal/social/groups.go`); the sweep (`sweepGroup`) looks at the host only. A silent member keeps counting toward `MaxMembers`, queue-visibility blocking and the readiness aggregate. (b) `members()` derives presence from `readiness_at_ms` alone, and `Heartbeat` does nothing for a non-host (`if m.role != "host" { return nil }`) although the route is documented as "Report presence" for every member. With the first-party follower sending no readiness reports until a title is loaded, every member of a lobby reads `away` after 30 s and `disconnected` after 120 s, the host included.
- Reason: `social_group_members` has exactly one per-member timestamp, `readiness_at_ms`, and it already means "when this member last reported readiness" (it is published as `reportedAt` and drives the documented 30-second stale rule). Recording a member heartbeat there would keep an old `ready` alive for as long as the app heartbeats, which weakens the readiness rule; recording it anywhere else needs a new column. So the correct fix is a migration, which this pass may not add. Part (a) additionally needs a decision the contract does not make: how long a silent member stays before the server moves them to `left`, and whether an `away`/`disconnected` member should hold the readiness aggregate (contract §11 lists `away | disconnected -> left` with no timing).
- Fix to make once that is allowed (about a day, server plus a small client change):
  1. Migration: `ALTER TABLE social_group_members ADD COLUMN seen_at_ms INTEGER NOT NULL DEFAULT 0` (backfill from `max(readiness_at_ms, joined_at_ms)`).
  2. Write it on every member-authenticated write: `Heartbeat` (all roles), `ReportReadiness`, `Join`, `CreateGroup`, and in `command`.
  3. `members()`: presence from `seen_at_ms` (30 s → `away`, 120 s → `disconnected`); keep `stale` on `readiness_at_ms`, but only count readiness at all while a title is loaded, and leave `disconnected` members out of the aggregate.
  4. `sweepGroup`/`settled`/`due`: move a non-host member silent for the decided period to `left` (`left_at_ms`, one `group.members` event), never the host (the host timeline already handles the host).
  5. Client: `packages/client-core/src/group-session.ts:284` comment "the server ends a silent membership on its own" becomes true; no behaviour change needed there.
  Note the interaction with B-13.1 (out of scope): every heartbeat already runs through `mutate`, which writes and bumps the group revision; adding `seen_at_ms` adds no extra transaction but is another reason to split that counter.
- Docs to update when fixed: `server/api/social.md` "Readiness" and the heartbeat description in `social.openapi.yaml`.

### B-13.19 — At the end of a title the group clock keeps running
- Status: SKIPPED (the contract-level fix is on the client; the server part is a product decision and has no reliable duration to use). Verified real.
- What I found: `extrapolate` (`internal/social/groups.go`) has no upper bound and nothing ends, pauses or advances a group when a title finishes; `timeline` carries no duration. Contract §13 rule 4 ("bounded to the playable timeline") is in the participant rules: it is the participant's target that must be bounded, and each participant knows its own playable length.
- Reason:
  1. To bound the clock on the wire without a client change the server would have to change the group's state when the title ends (pause at the end, stop, or advance the queue). Which of those is the terminal/advance policy the second review says must be chosen once, and it is tied to D-45 (queue advance, waiting). Picking "pause at end" here would pre-empt it.
  2. The server has no trustworthy duration for "the title as this group plays it": members may play different versions (contract §12.2), an item can have several asset links, `part_index` stacks, and `start_seconds`/`end_seconds` slices. `max(a.duration)` (what offline progress uses) is too short for a stacked title and would cut a film off for everyone; a safe upper bound is too long to fix the symptom.
- Fix to make (client lanes, about half a day, no decision needed): in `packages/client-core/src/group-session.ts` bound `GroupFollower.target()` to the local player's duration (add `durationSeconds` to `GroupPlayer.state()`), and in `tick()` treat a local player that has ended at or beyond the bounded target as in sync (`ready`) instead of reporting `buffering`; in `web/src/screens/together/Together.tsx` and native `Together.tsx` clamp the displayed position to `now.duration`. ### B-14.11 — An audiobook's position does not follow the listener to a later part
- Status: FIXED.
- What I found: real. `internal/downloads/progress.go` `applyProgress` ran `UPDATE book_resume SET position=… WHERE profile_id=? AND item_id=?`, which changes nothing unless the book's pointer already names that part, and never creates a pointer. Online, a session start upserts the pointer to its part (`internal/playback/personal_progress.go` `activatePersonalWriter`).
- Change: that statement is replaced by `followBook`. For an item that is a book part (kind 9 with a `catalog_book_files` row) it (1) updates the position when the pointer already names the part, as before; (2) otherwise moves the pointer to this part, or creates it, unless the part the pointer currently names has recorded activity (`progress_activity.updated_at`) at or after this observation. Because `applyProgress` has just written this part's own activity with the observation time, a batch of parts 3, 4, 5 ends on the latest one whatever order the entries arrive in. A moved pointer gets `playback_id=''`, so no stale online session keeps writing it and the next online play takes it through the existing ordinal fence. Films and other items are untouched. All lookups are by primary key.
- Scope note: this does not change the offline conflict rule (B-12.3, out of scope). It applies the rule `SyncProgress` already uses for a part's own position (newest observation or online activity wins) to the book-level pointer, so an old offline observation cannot pull a book back from a part reached online later. If Justin changes that rule, the pointer should follow the same rule; it is one comparison in `followBook`. Explicit-intent fences (`playback_personal_fences`) are not consulted here, exactly as the rest of the offline writer does not consult them (B-14.10, not on my list).

### B-14.15 — A "ready" download claim can point at a prepared file that no longer exists
- Status: SKIPPED (inseparable from B-14.1 / D-43(i), which are out of scope). Verified real.
- What I found: `preparedmedia.OpenDownloadArtifact` (`internal/preparedmedia/downloads_access.go`) refuses a version that is no longer `published`/`deleting` with `ErrUnavailable`; nothing in `internal/downloads` looks at prepared-version state after a claim is ready (`expire` in `worker.go` only checks retention time and a deleted catalogue item; `IssueGrant` trusts the ready row). So a later transfer fails with the generic prepared-media error while the claim stays `ready`, keeps its quota and keeps being offered.
- Reason: the only way to make the claim honest is to move it out of `ready`. In this package every such move revokes the claim's receipts (`terminal` → `revokeForPreparation`), and even without that call `Revalidate` refuses and revokes any receipt whose claim is not `ready` (`receipts.go`). So reconciling the claim also decides that a device which already holds a verified copy loses it because the server tidied its reusable bytes, which is exactly the open question in B-14.1 / D-43(i) (recommended answer there: no), and the second review says not to do that here. Today the stale `ready` row is what accidentally keeps those device copies renewable.
- Fix to make after D-43(i): (1) decouple receipt renewal from claim state for copies already on a device (or add a claim state such as `withdrawn` that renews but cannot transfer); (2) in `IssueGrant`/`OpenGrant` for `artifact_kind='prepared'`, check the version is `published` and, if not, move the claim to `unavailable` with `ReasonNotOptimized` (actions Retry/Remove; Retry re-prepares) inside the same transaction, and add the same check to `expire` for claims nobody is transferring; (3) map `preparedmedia.ErrUnavailable` on the transfer route to the downloads error envelope instead of the generic prepared-media one. A narrower variant I considered and rejected as speculative: reconcile only claims with no live receipt; it still races with a transfer that finishes just before its receipt is requested.

### B-14.16 — Receipt dead ends after server data loss
- Status: SKIPPED (the fix is on the client; the server already answers correctly).

### B-14.11, blocker — an older offline observation could take the book from a session that had just started
- Verified: real. My first test helper seeded progress, activity and pointer together and hid the window.
- Change (fe48dbc): `followBook` also reads the bound session's own evidence, `playback_observations.created_at` (stamped by the schema trigger when the session row is inserted) and `reported_at` (its last report), by the unique `session_id`. A move needs the observation to be newer than the part's activity and newer than both of those. A pointer whose session row is gone has no session evidence and falls back to activity, as before. No migration.
- Tests: `internal/downloads/progress_book_test.go` — `TestOfflineListeningDoesNotTakeTheBookFromASessionThatJustStarted` (sub-tests with no activity and with day-old activity on the session's part; asserts pointer and writer both stay, then that an observation made after the start does move the book and unbinds the session) and `TestOfflineListeningDoesNotTakeTheBookFromASessionStillReporting`.
