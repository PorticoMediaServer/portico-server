### B-07.1 — One permanently failing entity stops all second-tier derived workers
- Status: FIXED
- What I found: Real. `Worker.Step` (`internal/compactcatalog/derive.go`) picked any domain with a `catalog_dirty` row and reached `runSteps` only on `sql.ErrNoRows`; an id poisoned in memory keeps its row, so once only poisoned ids were left `drainDomain` re-read them, failed, and the step workers never ran again. I also confirmed (with a test) a second form the reviewers only hinted at: during a rebuild, a failing id is enumerated by `Backfill` in the same transaction as its drain, the cursor advance rolls back with the failure, so the rebuild never passes that id, `rebuilding` stays 1 (readers answer `ErrBuilding` forever) and, again, the step workers never run.
- Change: `Step` now selects only domains with work it can finish (rebuilding, or a queued id that is not set aside). With none, it runs the step workers; only when they are idle too does it retry one set-aside id (one at a time, so the id is named in the log and its in-memory mark is cleared exactly if it succeeds). A rebuild's enumeration no longer drains ids already set aside: it queues them, advances its cursor and moves on, so the rebuild finishes with the failing id still in `catalog_dirty`. The failure stays visible exactly as before: the id keeps its durable queue row, and each retry logs "Catalogue id N in domain D failed; it stays queued…" plus the loop's "will retry" line every five seconds. No schema change, so no durable diagnostics table (the second review's suggestion) and no change to the retry cadence.
- Commit: 50e71c8 "Keep derived step workers and rebuilds moving past an id that never derives"
- Tests: `internal/compactcatalog/derive_failure_test.go` — `TestStepWorkersRunBehindAnIDThatNeverDerives`, `TestRebuildFinishesPastAnIDThatNeverDerives` (both failed before the fix for the stated reason). `go test ./internal/compactcatalog/... ./internal/persistence/...` ok (includes the per-item statement seek guard and the statement scan guard); `go vet ./internal/compactcatalog/` ok.
- Not verified: behaviour under the real supervised `Run` loop with its 5 s back-off (the tests drive `Step` directly). The "lag while a long healthy drain is running" variant is unchanged by design.
- Docs to update: `Project Architecture/03 Catalogue and Metadata.md` line 22 area could say that a rebuild completes with a permanently failing id left queued (the domain then serves without that one entity's fresh derived rows). Reviewer attention: this is the one behavioural consequence of the fix — a domain leaves `ErrBuilding` with one entity's derived rows stale or missing instead of staying offline forever.

### B-07.5 — A search can fail with "the library changed" although it read one consistent snapshot
- Status: FIXED
- What I found: Real. `Service.Search` read its before and after revisions with `searchRevision(ctx, s.db, …)` on the raw handle (`internal/catalog/search.go`, the two call sites around the group loop) while the groups ran on the request's read snapshot (`httpapi` `compose`). Any library revision committed in between made the after-check differ and the first page was rejected with `ErrStaleContinuation`; the envelope's `revision` could also be newer than the rows it described.
- Change: both `searchRevision` calls now read through `s.read()`, which resolves the request's snapshot. On a snapshot the two reads are the same frame, so a first page can no longer be rejected by a concurrent publication, and the reported revision is the one the rows were read at. Without a snapshot (direct callers) the after-check still works as before. Continuation cursors are still checked against the revision, and the HTTP layer's authorisation fence is untouched. No retry loop was needed.
- Commit: 31239ca "Read a search's revision from the snapshot its results come from"
- Tests: `internal/catalog/search_snapshot_test.go` — `TestSearchOnOneSnapshotSurvivesConcurrentLibraryChanges` (commits a library revision bump between the search's groups; failed before with "catalog or viewer state changed; restart this query from its first page"). `go test ./internal/catalog/...` ok (143 s).

### B-07.8 — Date filters compare raw text
- Status: FIXED
- What I found: Real. `validBrowseDate` accepts `YYYY-MM-DD` or RFC 3339 and `browseCompiler.comparison` bound the operand as sent against stored UTC text (`internal/catalog/browse_expression.go`). `dateAdded` is stored with milliseconds (`catalogedNow`, `internal/catalog/discovery.go:90`), DVR publication stores RFC3339Nano, `lastPlayedAt` has seconds or nanoseconds, `releaseDate` is usually a bare date. So a day never equalled a timestamp, inclusive upper bounds dropped the last day, and an offset operand was compared character by character.
- Change: for `date` fields the compiler now turns the operand into the half-open range of stored text it names: the whole UTC day for `YYYY-MM-DD`, the second it falls in (after conversion to UTC) for an RFC 3339 instant. `equals` = inside the period, `not-equals` = outside or missing, `less-than` = before it, `at-most` = up to its end, `greater-than` = after it, `at-least` = from its start, `between` = from the first period's start to the last one's end. Bounds are plain text comparisons on the unwrapped column, so plans do not change and it is correct for every stored UTC format (date, seconds, milliseconds, nanoseconds). The node's value is not rewritten, so the query echo and saved views are unchanged. Instants are compared at one-second resolution because stored fractions vary in length and do not sort as text against each other.
- Commit: a69f685 "Compare browse date filters by day and instant instead of raw text"
- Tests: `internal/catalog/browse_date_test.go` — `TestBrowseDateFiltersCompareDaysAndInstants` (18 cases over `dateAdded`, `lastPlayedAt`, `releaseDate`; 11 failed before). `go test ./internal/catalog/... ./internal/livechannels/library/...` ok; `go vet ./internal/catalog/` ok.
- Not verified: web/native date-range controls against a running server. Days are UTC days (the API carries no viewer time zone); a stored value written with a non-UTC offset would still compare as text, but no writer produces one.
- Docs to update: `server/api/browse.openapi.yaml` (field `type: date`) does not describe operand semantics; a sentence on day/second periods would fit there. `Specs/Spec — Custom Channels Builder.md` line 52 (`recentDays` → `dateAdded at-least`) is unaffected in behaviour.

### B-08.2 — Any error a legacy handler does not recognise becomes an unlogged `400 invalid_request`
- Status: SKIPPED
- What I found: Real as described. `failure()` (`internal/httpapi/router.go`, from the line `status, code := 400, "invalid_request"`) overrides the default only for errors it names, and logs only when the final status is ≥ 500. So a wrapped internal error or a nil-dependency error (`errors.New("artwork unavailable")` and three similar ones in `httpapi`) is answered as the client's mistake and never logged.
- Reason (SKIPPED): the correct fix (default unknown causes to a logged 500) cannot be made without first naming every client-input error that currently relies on that same default, and that is well over a day and risky. Measured in this tree: `failure(w, …)` has 589 call sites in `internal/httpapi`, 507 of which pass through whatever a service returned; the service packages behind them contain roughly 400 unnamed `errors.New`/`fmt.Errorf` returns (catalog 169, metadata 107, playback 57, storage 42, …), and several exported input sentinels are also mapped only by the default (`catalog.ErrSearchQuery`, `ErrPersonQuery`, `ErrAdminQuery`, `ErrShowContext`, `identity.ErrDirectInput`, `metadata.ErrRepairInput`). Nothing in an error's type separates "the client sent something invalid" from "the server failed" for these, so flipping the default would turn an unknown number of legitimate 400s into 500s (with different client retry behaviour) wherever one is missed, which is exactly the "do not change the status of errors that are already mapped" constraint. I also decided against shipping only the logging half (log the unmapped branch at 400): the existing limiter keys on status and code, so one line per window would mostly show client typos, and it would write request-derived text into the server log; that is a choice for the owner, not a defect fix.
- Suggested path when it is taken up (about 2–3 days with review): (1) add a small marker (an `httpapi`-level `inputError` wrapper or an `IsInput` list of sentinels) and convert the input errors package by package, with a test per package; (2) only then flip the default to `500 internal` + `reportHTTPFailure`; (3) map the four nil-dependency errors in `httpapi` to a 503. Step 1 is mechanical but must be complete before step 2.
- Docs to update: none.

### What is still not closed

- **A legacy session that no request has ever classified keeps its rung's target in the fallback.** A legacy plan records no reach at its start (the legacy start route gives the playback package no admission result; that is the separate legacy-start gap), so the fallback cannot tell a LAN legacy session from a remote one until a subtitle request has classified it. Treating every such session as remote would have capped LAN legacy sessions at a remote limit, so I left that case as it was. v1 presentations are covered in every case, and legacy ones from their first classified request.
- **The fallback applies the member's cap and the owner's ceilings, not the upload budget.** The budget is computed in the HTTP layer from live v1 sessions and is applied on every request-driven path.
- **The member's cap is read when the fallback plans**, inside its transaction; a cap changed after that takes effect at the next re-plan.
- **An unobserved source rate now always gets an explicit output rate when its audio is converted**, which means such a track at 44.1 kHz is resampled to 48 kHz. Sources whose rate was observed are unaffected.
