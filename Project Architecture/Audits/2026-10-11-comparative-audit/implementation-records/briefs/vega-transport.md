The Vega app's SDK networking follows HTTP redirects by itself and offers no way to refuse one before it is followed, so a request carrying a credential could be replayed to wherever a server (or someone in the path on plain HTTP) redirects it. An earlier lane contained that by refusing, on Vega, every request that carries a credential. The result is that **the Vega app cannot sign in, restore a session, control playback or open authenticated streams at all**. That is not acceptable: Vega is a release platform, and the owner's stated position (programme brief, section 1) is that users may make choices that are less safe, that Portico cautions at most and never blocks, and that plain HTTP is allowed from anywhere. An app that cannot be used is the wrong trade.

## What to deliver, in this order
1. **Find out what Vega really offers.** Read the SDK's type declarations and native networking modules in `apps/vega/node_modules` (and its documentation if reachable): is there any supported way to control redirects (a fetch option that is actually honoured, a native HTTP or sockets module, a Turbo Module in native code you can write against the SDK headers present here, a WebSocket or streaming API)? Record exactly what exists, with file paths.
2. **If a real pre-follow refusal is possible, implement it** as the Vega transport for credentialed requests and authenticated streams (normal TLS validation, no cookie jar, no cache, bounded bodies, redirects refused before any credential leaves), behind the same transport interface the other platforms use.
3. **If it is not possible, restore authenticated operation on Vega with the strongest protection the platform allows**, and say plainly that it is weaker than the other platforms: send credentials only to the exact origin the person signed in to; put short-lived, narrowly scoped credentials on the wire wherever the protocol allows instead of long-lived ones; after every response compare the final address with the requested one, and if a redirect to another origin was followed treat the credential as exposed — discard the response, revoke and rotate the session with the server at once (or sign out if rotation fails), and tell the person in one plain sentence; never follow a redirect for sign-in, token refresh or pairing requests if the SDK lets you see a 3xx at all; keep the server-identity proof the clients already do before sending credentials to a remembered address. Remove the blanket refusal. Add a single quiet line in Vega's About or connection details saying this device cannot refuse redirects in advance, only if that fits an existing pattern (no new screens).
4. Tests for whichever path you build (the bridge has a device-free test suite: `apps/vega` tests, 72 passing at your start); keep `npx tsc --noEmit` clean in `apps/vega` and `apps/native` and the string lints clean; `packages/*` are copies and must not be edited (describe any shared change needed).
5. Report: what the SDK offers; what you built; the residual risk in two plain sentences the owner can read; device test notes.
