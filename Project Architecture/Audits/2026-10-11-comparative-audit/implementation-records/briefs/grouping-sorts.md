## What to deliver
1. An inventory in your report: every browse surface the server composes (library tabs, groupings, collections, people, saved views, search results, lists) with the sorts and filters each accepts today.
2. **One sort set and one filter set, accepted everywhere it is meaningful**: title, date added, release date, rating (community, critic, personal), runtime, last played, play count, random with a stable seed, and the kind-specific ones that exist (episode count, album, artist, track number, file size, resolution); filters for watched state, genre, year or decade, rating, resolution, dynamic range, audio language, subtitle language, favourites and list membership, missing, versions. For groupings (a list of genres, of series, of categories) the group list sorts by name, count and recent activity, and the titles inside a group take the full set.
3. Every accepted sort is served from an index or a maintained derived key with stable keyset paging at any library size (no offset paging, no sorting in memory beyond a bounded page); add derived keys where needed and bump the derivation version. A sort that truly cannot apply to a kind is omitted from that surface's advertised options, never rejected at request time for an option the surface advertised.
4. The browse-capabilities document tells clients exactly which sorts and filters each surface accepts, so screens build their controls from it. Update the `client-core` types and parsers. Screens are adapted later.
5. Restrictions still apply inside SQL for every new path; tests for paging stability under each sort and for restricted profiles.
