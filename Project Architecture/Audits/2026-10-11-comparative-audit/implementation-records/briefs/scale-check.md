## What to do
1. Find the existing performance fixtures and tier tests (`server/internal/catalogtest`, `performance_tier_test.go`, `testtier`, `write_amplification_test.go` and similar) and use them. Build synthetic libraries directly in a database under `/home/justin/projects/Portico/.worktrees/audit-implementation/_program/scratch/scale-check/` at three sizes (about 10 thousand, 200 thousand and 2 million titles, with realistic shapes: films with one to three versions, shows with seasons and episodes, music with albums and tracks, several profiles with watch state, some restricted).
2. Measure and tabulate in your report, at each size: a derived-data rebuild from empty and after a derivation version bump (time, and that browse and search keep answering throughout); adding 1,000 titles to an existing library (time to appear, write amplification); every browse surface with every advertised sort and filter, first page and a deep page (latency, rows examined: use `EXPLAIN QUERY PLAN` and the planner statistics); search as-you-type queries; Home for a profile; Continue Watching; the needs-attention and missing lists; marking a 500-episode show watched and undoing it; removing a library; the event feed under a burst of 10,000 changes; database size, and reclamation after a large delete; memory of the server process during each.
3. **Fix what does not scale**: any request whose work grows with the library (a scan of a whole table, an in-memory sort, an offset page, a per-row query in a loop), any transaction that holds the write gate for seconds, any rebuild step that is quadratic, any missing index. Smallest sound fix with a test at the tier level so it cannot regress. Bump derivation versions where derived content changes.
4. Report the before and after numbers, what you fixed, and what remains slow and why (with a recommendation).
