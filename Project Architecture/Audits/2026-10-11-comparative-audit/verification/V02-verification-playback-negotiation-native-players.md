### B-02.1 Native devices are told HEVC may travel in MPEG-TS HLS
- **Claim:** The v1 translation invents HEVC support for Apple MPEG-TS HLS and prefers that transport when an HEVC file needs remuxing.
- **What I traced:** Native startup publishes v1 capabilities (`apps/portico-react-native/apps/native/src/bridge/useNativePlayback.ts:97`, `:127`); the native builder calls the shared converter (`apps/portico-react-native/apps/native/src/bridge/audio-decode.ts:25`). The original Apple table restricts TS video to H.264 (`apps/portico-server/packages/client-core/src/client-profile.ts:134`). The converter preserves only HLS booleans, and the server rebuilds TS video with HEVC included (`apps/portico-server/server/internal/playbackv1/capabilities.go:289`). That stored profile wins (`apps/portico-server/server/internal/playback/client_profile.go:466`); TS is tried first (`apps/portico-server/server/internal/playback/delivery_decision.go:308`) by the copy route (`apps/portico-server/server/internal/playback/delivery_plan.go:415`). Server TS output permits HEVC too (`apps/portico-server/server/internal/playback/delivery_decision.go:299` in that package).
- **Verdict:** **Confirmed, narrower.** The incorrect capability and route selection are established. An eligible HEVC MKV with copyable audio can take TS, but not every HEVC MKV does: SDR-screen HDR rejection, unsupported audio, ceilings and prior route exclusions can change the route. I did not establish an AVPlayer failure or the exact three-retry sequence. Cheapest device check: play one HEVC/AAC MKV on Apple TV with a compatible display, inspect the presentation container and whether first-frame playback succeeds; TS confirms the planning mismatch, an engine rejection confirms device impact.
- **Class:** **Defect** — contradicts the explicit Apple transport table and PC-PLAYBACK P04 fidelity requirement, rather than an owner trade-off.
- **Severity:** **High** — eligible Apple remux playback risks avoidable recovery/conversion; physical failure remains unproved.
- **Fix direction:** Preserve per-transport codec restrictions through v1, preferably one faithful capability representation; do not infer HEVC-in-TS merely from HEVC decoding. **Size: M**; shared `playback-v1/capability-profile.ts`, server `playbackv1/capabilities.go` and capability/route fixtures. **Backlog:** no matching entry.
- **Related:** B-02.5 describes the same flattening family; B-20.2/B-02.4 can mask this route for HDR on SDR displays. Those claims agree but need different fixes.

### B-02.2 Passthrough codecs are always rejected for v1-publishing devices
- **Claim:** Native passthrough flags survive v1 translation but their output route does not, so the planner rejects bitstream audio.
- **What I traced:** Android receiver encodings are probed (`apps/portico-react-native/apps/native/android/app/src/main/java/tv/getportico/portico/native/PorticoCapabilities.kt:240`), merged as passthrough (`apps/portico-server/packages/client-core/src/client-profile.ts:499`), and copied by the v1 builder (`apps/portico-server/packages/client-core/src/playback-v1/capability-profile.ts:49`). `CapAudio` and the capability document carry no output route; translation builds `AudioOutput` with only the largest codec channel count (`apps/portico-server/server/internal/playbackv1/capabilities.go:277`). Profile precedence is at `apps/portico-server/server/internal/playback/client_profile.go:466`; the rejection is at `apps/portico-server/server/internal/playback/delivery_decision.go:215`. Conversion's digital-output alternative also requires a route (`:362`).
- **Verdict:** **Confirmed, narrower.** Every *passthrough-marked* codec in this translated profile fails the route check. Decoded AC-3/E-AC-3 entries without that flag remain usable. Conversion normally chooses AAC; if conversion is disabled or unavailable playback can instead be refused. The output channel count can also be overstated, but actual soundbar downmix and Atmos output require device observation. Declared planner tests with an HDMI route do not exercise this translation.
- **Class:** **Defect**, contrary to P04 preserving compatible source audio.
- **Severity:** **High** (first pass Medium–High) — receiver users can lose bitstream fidelity or playback when conversion is unavailable.
- **Fix direction:** Add faithful active output-route and channel facts to v1 and keep decoding distinct from passthrough support. **Size: M**; capability schemas/builders, server translator, Android probe merge and translated-profile fixtures. **Backlog:** no matching entry.
- **Related:** Exact duplicate of B-20.1; merge implementation work. B-20.20 is a separate probe/merge problem that must be considered during that repair.

### B-02.6 Quality, version and audio re-plan parameters are dropped
- **Claim:** User choices arrive at shared playback but never enter the session request.
- **What I traced:** The web installs `V1QueuePlayer` (`apps/portico-server/web/src/player/engine.tsx:121`) and calls its `playItem` (`:225`). Quality/version handlers supply the values (`apps/portico-server/web/src/player/Player.tsx:347`, `:358`). Shared playback forwards them (`apps/portico-server/packages/client-core/src/index.ts:1095`), but `playItem` discards all three (`apps/portico-server/packages/client-core/src/playback-v1/v1-queue-player.ts:275`) and creates a queue with state only (`:332`). Native installs that same queue implementation (`apps/portico-react-native/apps/native/src/bridge/useNativePlayback.ts:113`). Session mutation helpers exist at `apps/portico-server/packages/client-core/src/playback-v1/sessions.ts:327`; searched call sites did not provide an alternate player-menu path. Audio switching has a distinct in-file branch (`apps/portico-server/packages/client-core/src/index.ts:858`).
- **Verdict:** **Confirmed, narrower.** Quality and prepared-version choices are dropped on the active queue path; audio is dropped when it requires server replanning. In-file audio switching is not covered by this defect. The first pass’s separate statement that failure escalation is unaffected is wrong on adopted queue paths; see N-V02.1. This does not mean the server API cannot accept quality limits: third-party callers can send them. The no-queue fallback also ignores the supplied choices.
- **Class:** **Defect** — working controls are promised by P03/P06 and the Title Pages spec's “choice travels with Play” rule.
- **Severity:** **High** — first-party users cannot apply the advertised video delivery choices, including lowering quality through this menu.
- **Fix direction:** Translate menu selections to v1 quality/version/audio IDs, mutate the current session for replans and preserve queue membership; carry initial choices on start. **Size: M**; shared queue player/session adapter, web/native choice handlers. **Backlog:** only the separate missing same-title source merge is listed, not this dropped-choice defect.
- **Related:** B-17.2 agrees that these restarts discard the queue; repair both together. B-04.24 and B-21.9 concern adjacent pre-play subtitle choices, not the same root cause. B-02.12 becomes more exposed when quality limits are connected.

### B-02.7 Headerless starts take legacy admission without bitrate ceilings
- **Claim:** Omitting `Idempotency-Key` selects a deprecated start that discards member bitrate caps and allows Original to remove owner ceilings.
- **What I traced:** Shared POST dispatch is wired at `apps/portico-server/server/internal/httpapi/playback_sessions.go:13`; only the header selects v1 (`apps/portico-server/server/internal/httpapi/playback_v1.go:332`, `:349`). Legacy admission runs but ignores its returned cap (`apps/portico-server/server/internal/httpapi/playback_sessions.go:38`), then calls legacy creation (`:42`). That path uses a rung target unless `V1Choice` exists (`apps/portico-server/server/internal/playback/service.go:169`); Original zeros video/audio/height ceilings (`apps/portico-server/server/internal/playback/quality_ladder.go:176`). Creation still applies owner stream/transcoding policy (`apps/portico-server/server/internal/playback/service.go:374`, `:393`). The legacy row expires after 12 hours (`:409`); admin listing reads v1 rows (`apps/portico-server/server/internal/playbackv1/admin.go:60`).
- **Verdict:** **Confirmed, narrower.** This is an active authenticated route, not an unwired compatibility shim. The first pass overstates slot lifetime: `countPlaybackSlots` also requires unexpired, unrevoked access authorization (`apps/portico-server/server/internal/playback/v1_session_helpers.go:54`), so the 12-hour delivery-row expiry does not prove a full 12 hours of counted capacity. Restrictions and stream-count/transcoding controls still apply; the bypass is the returned member bitrate cap plus Original's owner delivery ceilings and v1 lifecycle/admin visibility. A caller needs the legacy body, including `requestId`, not just a missing header on an unchanged v1 body. Original must remain selectable for the source (the legacy ladder can disable it for an oversized source when conversion is off). The inspected v1 admission tests use the header, so they do not disprove it.
- **Class:** **Defect** — deprecated compatibility does not authorize unenforced owner/member controls; protocol binding rules require limits on every session.
- **Severity:** **High** (first pass Medium–High) — a signed-in member with a cap can deliberately escape it and leave an occurrence outside v1 Now Playing/lease management.
- **Fix direction:** Remove legacy start dispatch, or adapt it to the same v1 admission, ceilings, counted session and lease. **Size: M**; HTTP playback dispatch, session creation and admission tests. **Backlog:** no matching entry.
- **Related:** B-02.12 independently loses ceilings during subtitle replanning; they agree about policy inconsistency but are different entry points.

### B-02.20 `ended` marks watched regardless of position
- **Claim:** A premature terminal end can mark an unfinished title watched and clear resume.
- **What I traced:** v1 accepts a fresh report from the playing device, including `ended`, with generation/sequence checks (`apps/portico-server/server/internal/playbackv1/sessions_change.go:263`, `:291`, `:324`), then calls playback progress (`:330`). Playback checks occurrence authority and canonical writer (`apps/portico-server/server/internal/playback/service.go:589`, `:624`). Catalog completion has an unconditional terminal branch (`apps/portico-server/server/internal/catalog/personal_activity.go:66`), but personal state is written only when history is active, canonical and unfenced (`:82`, `:112`). The saved-state contract explicitly accepts terminal completion (`portico-internal/Product Contracts/saved-state-and-downloads/contract.md:86`).
- **Verdict:** **Confirmed, narrower.** Terminal evidence bypasses the percentage test, but arbitrary/stale/foreign reports do not clear a viewer's state. No inspected path proves a supported engine reports a failed segment as a successful end. The defect claim therefore remains a contingent trust risk, not established false completion in normal playback. Cheapest experiment: on an isolated test instance later, serve a VOD presentation cut short while its advertised duration remains long, observe whether the first-party engine sends `ended` or `error`, and read watched/resume state; `ended` plus cleared resume proves the risk.
- **Class:** **Design risk** — accepting terminal completion is specified; whether engine evidence is sufficiently trustworthy needs acceptance testing.
- **Severity:** **Low** (first pass Low–Medium) — affects personal completion only if fresh canonical playback falsely ends early.
- **Fix direction:** Define “successful end” evidence and distinguish truncation from completion before adding a position guard; preserve legitimate endings with inaccurate durations. **Size: M**; native/web terminal reporting, v1 timeline, catalog progress and media fixtures. **Backlog:** no matching entry.
- **Related:** Exact duplicate B-12.8 agrees; merge. This is distinct from B-02.8, whose rewatch behavior is explicitly deliberate.

### B-20.3 Plain HTTP subtitles are rejected

- **Related:** B-20.13 shares silent status dropping; B-22.18 concerns auxiliary media fetches bypassing route verification and must be considered when repairing URL authorization. They agree but are not duplicates.

### B-20.9 HEVC sample-entry compatibility is unchecked
