## Partly present — details

Each paragraph below describes the implemented slice and remaining scope. These are source findings, not runtime acceptance.

**F-14.2 — Resumable downloads.** The server-side byte-range work is already present. The remaining problem is identity across renewed grants: restarting under a fresh URL discards otherwise valid partial bytes. Apple background-task recovery and Android range recovery need different adapters for the same artifact contract.

**F-14.3 — Download retry and waiting states.** Pending preparation collection, a background URLSession and manual retry do not supply a condition-driven retry state machine. A retryable network or storage condition should remain a waiting state and reattempt only when permitted, with durable attempt/owner fencing.

**F-14.5 — Offline artwork.** Keeping an artwork URL or relying on the incidental native image cache can make a warm offline screen appear to work. It does not establish that art is retained after process death or cache eviction. Download-owned verified local art and shared reference retention remain the deliverable.

**F-14.6 — Offline metadata catalogue.** This is an incomplete snapshot, not an absence of all local title metadata. Requests made from a detail page retain a readable title and subtitle; expanded containers can fall back to an artifact filename because their per-member display was never populated. Show/album/book identity and ordering must be server-authored and stored with the artifact.

**F-14.8 — Offline library browsing.** The assertion that downloads are reachable only after a server failure is wrong: the normal signed-in Downloads destination embeds the local list. Remaining work is grouped browsing, local query/sort and optional offline navigation, not adding another entry point.

**F-14.11 — Rolling offline rules.** The existing rule is completion-triggered next-after download, with optional deletion of watched local files. A rolling keep-N subscription is different: it tracks a durable selection, fills ahead, responds to new episodes and changes, and reconciles storage while the app reconnects.

**F-14.12 — Offline personal mutations.** A durable journal of observed playback is already implemented. Explicit offline edits need operation identity, base revision and conflict evidence; using the playback journal for a deliberate Unwatched/My List/rating action would erase the distinction the contract requires.
